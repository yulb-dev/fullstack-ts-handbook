# 第 8 章 · 懒加载与路由级代码拆分（route lazy）

> 本章目标：**用 route `lazy` + 动态 `import()` 做路由级代码拆分**，把首屏包体积压下来，只在用户真正访问某路由时才加载它的代码。
> 对应验收项：⑧-a
> 预计用时：45 分钟

---

## 8.1 问题：不拆分会怎样

到目前为止，我们的 `router.tsx` 是这样导入所有页面的：

```tsx
import Home from "./routes/home";
import ConcertsCity from "./routes/concerts/city";
import ConcertDetail from "./routes/concerts/detail";
import AdminReport from "./routes/admin/report"; // 假设它引入了一个 200KB 的图表库
// ...
```

静态 `import` 意味着：**打包器把所有路由的代码（以及它们引入的重型依赖，如图表库、富文本编辑器、Markdown 渲染器）统统塞进首屏 JS 包。**

后果：用户只是想看看首页，却要先下载**整个应用**（包括他可能永远不会访问的管理后台、图表库）的代码。首屏变慢，尤其在弱网/移动端。

💡 **目标**：首屏只加载「首屏需要的代码」。用户导航到 `/admin/report` 时，**再按需**去下载那个路由的 chunk。这就是「路由级代码拆分（route-based code splitting）」——它是 SPA 性价比最高的性能优化之一。

---

## 8.2 route `lazy`：路由的「按需加载」

React Router 在 Data Mode 提供 `lazy` 属性：**把路由的大部分定义（组件、loader、action、错误边界等）延迟到「路由首次被匹配时」再动态加载。**

它有**两种写法**。

### 写法 A：函数式（返回一个包含所需字段的对象）

```tsx
createBrowserRouter([
  {
    path: "/admin/report",
    // path 必须静态（见 8.4），其余交给 lazy
    lazy: async () => {
      // 并行加载组件与 loader，加载完再渲染
      const [Component, loader] = await Promise.all([
        import("./routes/admin/report"),
        import("./routes/admin/report-loader"),
      ]);
      return { Component: Component.default, loader: loader.loader };
    },
  },
]);
```

### 写法 B：对象式（每个字段各自 lazy，粒度更细）

```tsx
createBrowserRouter([
  {
    path: "/concerts/:city/:concertId",
    lazy: {
      // 每个属性是一个「返回该属性值」的异步函数
      Component: async () => (await import("./routes/concerts/detail")).default,
      loader: async () => (await import("./routes/concerts/detail")).loader,
      action: async () => (await import("./routes/concerts/detail")).action,
    },
  },
]);
```

两种写法等价，按喜好选。对象式的好处是可以「只 lazy 组件，loader 保持静态」（loader 通常很小，没必要拆）。

> ⚠️ **返回的字段名要严格对应 Route Object 的字段名**，且组件/边界是**首字母大写**的 `Component` / `ErrorBoundary`，函数是**小写**的 `loader` / `action` / `shouldRevalidate`。写错名字会被静默忽略。
> 若源文件用 `export default`，记得取 `.default`；用 `export function loader`，则取 `.loader`。

## 8.3 lazy 的执行时机与「只跑一次」

- **何时执行**：当一次导航**匹配到**该路由、准备渲染它时，React Router 先 `await` lazy 把定义加载回来，再执行 loader、再渲染组件。
- **只执行一次**：`import()` 的模块会被浏览器/打包器**缓存**。第二次访问同一路由不会重新下载（除非你清了缓存）。所以 lazy 的开销只发生在「首次进入」。
- **配合 pending UI**：lazy 加载期间，`useNavigation().state` 会是 `"loading"`。第 5 章的全局进度条/Spinner 天然覆盖了「正在下载路由代码」这段时间——**用户看到的是统一的加载反馈**，你不用为 lazy 单独写 loading。

```tsx
// 根布局的全局 spinner 会在「下载 lazy chunk + 跑 loader」全程显示
const navigation = useNavigation();
const isNavigating = Boolean(navigation.location);
```

## 8.4 哪些字段**不能** lazy（必须静态）

路由器要**先匹配 URL、再决定加载谁**，所以「用于匹配和构建路由树」的信息必须在创建 router 时就已知，**不能 lazy**：

| 必须静态 | 可以 lazy |
| --- | --- |
| `path`、`index`、`children`、`id`、`caseSensitive` | `Component`、`loader`、`action`、`ErrorBoundary`、`shouldRevalidate`、`handle`、`lazy` 本身 |

也就是说：**路由的「骨架」（谁匹配什么 URL、层级关系）是静态的；路由的「血肉」（组件、数据逻辑）可以按需加载。** 这既保证了匹配的高效，又实现了代码的按需。

---

## 8.5 拆分策略：怎么拆才划算

不是「每个路由都无脑拆」就最好。策略建议：

1. **首屏/高频路由可以先不拆**（如首页、登录页），避免用户第一跳就等一次网络下载。把它们留在主包，反而更快。
2. **重型 / 低频路由一定要拆**：管理后台、报表（图表库）、富文本编辑器、设置页深处、支付流程等。
3. **把重依赖关进路由文件**：只有被某个 lazy 路由引用的大依赖，才会被打进那个 chunk。若在多个路由共享，考虑抽成「共享 chunk」或延迟到用时再 `import()`。
4. **loader 是否拆看情况**：loader 一般很小，可以不拆（保持静态），这样导航时不必等「先下载 loader 文件、再跑 loader」两跳。若 loader 依赖了很重的库，则值得拆。
5. **预加载（可选进阶）**：可以在鼠标 hover 到链接、或空闲时提前 `import()` 目标路由的 chunk，抵消首次进入的下载延迟。Framework Mode 的 `<Link prefetch>` 内建此能力；Data Mode 可手动实现。

### 一个「务实」的拆分示例

```tsx filename=src/router.tsx
import { createBrowserRouter } from "react-router";
import Root from "./routes/root";
import Home, { loader as homeLoader } from "./routes/home"; // 首页：静态，进主包

export const router = createBrowserRouter([
  {
    path: "/",
    Component: Root,
    ErrorBoundary: () => import("./routes/root-error").then((m) => m.default), // 也可 lazy
    children: [
      { index: true, Component: Home, loader: homeLoader }, // 首屏，不拆

      {
        // 低频、重型：管理后台报表，拆！
        path: "admin/report",
        lazy: async () => {
          const mod = await import("./routes/admin/report");
          return { Component: mod.default, loader: mod.loader };
        },
      },

      {
        // 详情/编辑：拆组件，loader 保持静态（很小）
        path: "concerts/:city/:concertId/edit",
        lazy: {
          Component: async () => (await import("./routes/concerts/edit")).default,
        },
        loader: editLoader, // 静态
      },
    ],
  },
]);
```

## 8.6 验证拆分是否生效

用 Vite 打包并查看产物：

```bash
npm run build
```

在输出的 chunk 列表里，你应该看到**除了主包外，多出若干按路由切分的小 chunk**（文件名通常带 hash，如 `report-3f9a2c.js`）。若所有代码都在一个巨大的 `index-xxxx.js` 里，说明拆分没生效（检查是否误用了静态 `import`）。

进一步，可用体积分析工具（如 `rollup-plugin-visualizer`）可视化每个 chunk 里装了什么，确认重型依赖确实被隔离到了对应路由 chunk：

```bash
npm i -D rollup-plugin-visualizer
```

```ts filename=vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { visualizer } from "rollup-plugin-visualizer";

export default defineConfig({
  plugins: [react(), visualizer({ open: true, gzipSize: true })],
});
```

🧪 **动手实践**：给 Concert Hub 的「管理报表」路由加一个假的「重依赖」（比如 `import` 一个只在它内部用到的大工具函数），做 lazy 拆分，然后 `npm run build` 对比拆分前后的主包体积变化。用 Network 面板确认：首次访问 `/admin/report` 时才下载那个 chunk。

## 8.7 与其它概念的关系（小结）

- **lazy 与 loader 的并行**：lazy 内部用 `Promise.all([...import()])` 让组件和 loader 文件并行下载；下载完成后，loader 再按第 5 章的规则与父/兄弟 loader 并行执行。
- **lazy 与错误边界**：lazy 加载失败（网络断了、chunk 404）也是一次「路由错误」，会走到最近的错误边界——所以**根错误边界（第 6 章）在做了 lazy 后更重要**，它能兜住「代码没下载下来」的情况。
- **lazy 与测试**：第 9 章会用 `createRoutesStub`，测试时通常直接给静态的 `Component`/`loader`，不走 lazy（避免测试里去解析动态 import）。

## 🔧 常见坑 / 排错

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 打包后只有一个巨大 chunk | 仍在用静态 `import` 导入路由组件 | 改成 `lazy` + 动态 `import()` |
| lazy 返回了组件但页面空白 | 字段名写错（如返回 `component` 小写） | 用大写 `Component`；`export default` 要取 `.default` |
| 报「path 不能 lazy」类错误 | 试图把 `path`/`children` 放进 lazy | 匹配字段保持静态，只 lazy 组件/数据逻辑 |
| 首次进入某路由有明显等待 | lazy chunk 需下载 | 结合 pending UI；或对高频路由做 hover/空闲预加载 |
| 弱网下 lazy chunk 加载失败白屏 | 没有根错误边界兜住加载失败 | 加根 `ErrorBoundary`（第 6 章） |
| 拆分后首屏反而更慢 | 把首屏/高频路由也拆了，第一跳要下载 | 首屏路由留在主包，只拆重型低频路由 |
