# 第 6 章 · 错误处理与错误边界

> 本章目标：**用错误边界（ErrorBoundary / errorElement）优雅地兜住一切错误，并清楚区分三类完全不同的错误：资源不存在（404）、权限拒绝（403）、意外崩溃（500）。**
> 对应验收项：⑥
> 预计用时：50 分钟

没有错误处理的应用，一出错就是白屏。这一章让你的应用「就算出错也体面」。

---

## 6.1 错误边界是什么

React Router 会**自动捕获** loader、action、以及组件渲染过程中抛出的错误，然后渲染**离错误最近的那个「错误边界」**，而不是让整页白屏。

在 Data Mode，错误边界通过 Route Object 的两种等价写法之一声明：

- **`ErrorBoundary`**：一个**组件**（推荐，可读性好）。
- **`errorElement`**：一个 **JSX 元素**（`errorElement: <MyError />`）。

⚠️ 关键区别：**在 Data Mode，`ErrorBoundary` 组件不会通过 props 收到 error**，要用 hook `useRouteError()` 去取。（在 Framework Mode 里才会以 prop 形式传入。）

```tsx filename=src/router.tsx
import { createBrowserRouter } from "react-router";

const router = createBrowserRouter([
  {
    path: "/",
    Component: Root,
    ErrorBoundary: RootErrorBoundary, // 根部兜底错误边界
    children: [/* ... */],
  },
]);
```

## 6.2 一个「什么都能兜住」的根错误边界

官方建议：**每个应用至少要有根部错误边界**，它能处理三种主要情况：
1. 用 `data()` 抛出的、带状态码的「业务错误响应」；
2. `Error` 实例（有堆栈的意外异常）；
3. 随手抛出的其它任意值。

```tsx filename=src/routes/root-error.tsx
import { isRouteErrorResponse, useRouteError, Link } from "react-router";

export default function RootErrorBoundary() {
  const error = useRouteError();

  // 情况 1：来自 loader/action 的 data()（带 status）——可控的业务错误
  if (isRouteErrorResponse(error)) {
    return (
      <main>
        <h1>{error.status} {error.statusText}</h1>
        <p>{typeof error.data === "string" ? error.data : "请求失败"}</p>
        <Link to="/">回到首页</Link>
      </main>
    );
  }

  // 情况 2：真正的 JS 异常（代码 bug、网络错误等）
  if (error instanceof Error) {
    return (
      <main>
        <h1>出错了</h1>
        <p>{error.message}</p>
        {/* 生产环境不要把 stack 直接展示给用户，见 6.6 */}
        <pre>{error.stack}</pre>
        <Link to="/">回到首页</Link>
      </main>
    );
  }

  // 情况 3：抛出了不明所以的值
  return (
    <main>
      <h1>未知错误</h1>
      <Link to="/">回到首页</Link>
    </main>
  );
}
```

- `useRouteError()`：返回被边界捕获的错误（类型是 `unknown`，**必须先判类型再用**）。
- `isRouteErrorResponse(error)`：类型守卫，判断它是不是「由 loader/action 抛出的、带状态码的错误响应」。是的话可以安全访问 `error.status`、`error.statusText`、`error.data`、`error.internal`。

## 6.3 三类错误，三种 UI（本章重点）

用户遇到的「错误」其实语义完全不同，UI 也应该完全不同。**区分它们的方式，就是你在 loader/action 里「怎么抛」。**

### (A) 资源不存在 → 404（not found）

**场景**：URL 结构合法，但请求的那条数据不存在（`/concerts/chicago/999` 里没有 id=999 的演出）。

在 loader 里，当查不到数据时 **`throw data(..., { status: 404 })`**：

```tsx filename=src/routes/concerts/detail.tsx
import { data } from "react-router";

export async function loader({ params }) {
  const concert = await getConcert(params.concertId);
  if (!concert) {
    throw data("找不到这场演唱会", { status: 404 });
  }
  return { concert };
}
```

- 这会走到错误边界的 **`isRouteErrorResponse`** 分支，`error.status === 404`。
- UI 应该友好：「没找到这个内容」+ 一个返回列表的链接，**而不是**显示技术堆栈。

> 💡 **两种 404 要分清**：
> 1. **URL 根本没匹配到任何路由**（如 `/whatever`）→ 用第 2 章的 `{ path: "*", Component: NotFound }` 兜底路由处理。
> 2. **URL 匹配到了路由，但数据不存在**（如 `/concerts/x/999`）→ 在 loader 里 `throw data(..., {status:404})`。
> 两者最终都想显示「404」，但触发路径不同，别混为一谈。

### (B) 权限拒绝 → 403（forbidden）

**场景**：数据存在，但当前用户无权查看（普通用户访问管理页）。

```tsx
export async function loader({ request, params }) {
  const user = await getUser(request);
  if (!user) return redirect("/login");           // 没登录 → 改道（不是错误）
  if (user.role !== "admin") {
    throw data("你没有权限访问该页面", { status: 403 }); // 登录了但无权 → 403 错误
  }
  return { report: await getAdminReport(params.id) };
}
```

错误边界里可以针对 `error.status === 403` 给出「无权限，申请权限 / 换账号」的 UI，与 404 区分开。

> 💡 **未登录用 `redirect("/login")`，无权用 `throw data(403)`**。前者是「你该去别的地方」，后者是「你被拒绝进入这里」。语义不同，处理也不同。

### (C) 意外异常 → 500（bug / 网络等）

**场景**：代码有 bug（`undefined is not a function`）、后端 500、网络断开。这些**不是你主动抛的**，而是自然发生的 `Error`。

- 它们会落到错误边界的 **`error instanceof Error`** 分支。
- UI 应该道歉 + 提供重试/回首页，**开发环境**可显示 message/stack 帮你排查，**生产环境**要隐藏技术细节（见 6.6）。

### 三类的统一分发（更实用的根边界写法）

```tsx
export default function RootErrorBoundary() {
  const error = useRouteError();

  if (isRouteErrorResponse(error)) {
    switch (error.status) {
      case 404:
        return <NotFoundPage message={asString(error.data)} />;
      case 403:
        return <ForbiddenPage message={asString(error.data)} />;
      case 401:
        return <UnauthorizedPage />; // 例如引导重新登录
      default:
        return <GenericHttpError status={error.status} message={asString(error.data)} />;
    }
  }

  if (error instanceof Error) {
    return <UnexpectedError error={error} />; // 生产环境隐藏 stack
  }

  return <UnknownError />;
}

const asString = (v: unknown) => (typeof v === "string" ? v : "请求失败");
```

| 你的意图 | 在 loader/action 里怎么写 | 错误边界如何识别 | 典型 UI |
| --- | --- | --- | --- |
| 数据不存在 | `throw data("...", { status: 404 })` | `isRouteErrorResponse` 且 `status===404` | 友好的「没找到」+ 返回链接 |
| 无权限 | `throw data("...", { status: 403 })` | `isRouteErrorResponse` 且 `status===403` | 「无权限」+ 申请/换号 |
| 未登录（改道） | `return redirect("/login")` | **不进错误边界**，直接导航 | 登录页 |
| 代码 bug / 500 | 自然抛 `Error` | `error instanceof Error` | 道歉 + 重试，隐藏 stack |

## 6.4 嵌套错误边界：「最近的一个」生效

错误会**冒泡到最近的、定义了错误边界的路由**。这让你能给不同区块定制不同的错误 UI，同时用根边界兜底。

```tsx
createBrowserRouter([
  {
    path: "/app",
    Component: App,
    ErrorBoundary: AppErrorBoundary, // ✅ 有边界
    children: [
      {
        path: "invoices",
        Component: Invoices, // ❌ 没有边界
        children: [
          {
            path: ":id",
            Component: Invoice,
            ErrorBoundary: InvoiceErrorBoundary, // ✅ 有边界
            children: [
              { path: "payments", Component: Payments }, // ❌ 没有边界
            ],
          },
        ],
      },
    ],
  },
]);
```

错误来源与最终渲染的边界：

| 错误发生在 | 渲染哪个边界 |
| --- | --- |
| `App` | `AppErrorBoundary` |
| `Invoices` | `AppErrorBoundary`（自己没有，向上找） |
| `Invoice` | `InvoiceErrorBoundary` |
| `Payments` | `InvoiceErrorBoundary`（自己没有，向上找最近的） |

💡 设计建议：
- **根部**放一个「万能兜底」边界（6.2 那个）。
- **关键区块**（如账单详情）放**专属**边界，出错时只让该区块显示错误，父布局/导航仍在，用户不会「整个应用都没了」。

> ⚠️ 如果一个路由既没有自己的边界，祖先也全都没有，React Router 会用一个**内置的默认错误界面**。别依赖它——务必至少在根部放一个。

## 6.5 错误边界**不是**用来做表单校验的

再强调一次（第 4 章也提过）：

- **表单字段校验错误**（标题太短、邮箱格式不对）→ action 里 `return { errors }`，组件用 `useActionData()` 读，**内联显示在输入框旁**。这是「正常流程」，不是异常。
- **错误边界**（本章）→ 处理「页面无法正常渲染」级别的问题：404、403、崩溃。

把校验错误 `throw` 到错误边界，会让用户看到整页错误、还得重新填表——体验很差。**分清「可恢复的输入问题」和「不可恢复的页面问题」。**

## 6.6 生产环境的错误脱敏与上报

- 📌 **Framework Mode** 在生产构建时，会**自动脱敏**服务端抛出的 `Error`（浏览器端只收到通用 message、没有 stack），防止泄露服务端信息。但 `throw data(yourData)` 里的 data **不会**被脱敏——因为它本就是「打算渲染给用户看」的内容。
- **Data Mode** 没有这层自动脱敏，所以**你要自己注意**：在 `error instanceof Error` 分支，生产环境**不要**把 `error.stack` / 敏感 `message` 渲染给用户。用环境判断：
  ```tsx
  {import.meta.env.DEV && error instanceof Error && <pre>{error.stack}</pre>}
  ```
- **错误上报**：错误边界不是「上报」的地方，但你可以在边界组件里（`useEffect`）把 `error instanceof Error` 的意外异常发给 Sentry 等；业务错误响应（4xx）通常**不需要**上报（那是预期内的）。
- **官方立场**：不推荐「故意抛错来强制渲染错误边界」当作常规控制流——错误边界主要用于**捕获意外**。唯一推荐的「故意抛」就是 404/403 这类 `throw data(...)`。

## 6.7 动手实践：给 Concert Hub 加全套错误处理

🧪 步骤：
1. 在**根路由**挂 `RootErrorBoundary`（用 6.3 的统一分发版本）。
2. 详情页 loader：查不到就 `throw data("找不到这场演唱会", { status: 404 })`。
3. 造一个「管理报表」路由，loader 里模拟无权：`throw data("无权限", { status: 403 })`。
4. 在某个 loader 里临时写 `return undefined()` 制造一个真 bug，验证它落到 `error instanceof Error` 分支。
5. 用第 2 章的 `{ path: "*", Component: NotFound }` 处理「URL 没匹配到」。

```tsx filename=src/routes/not-found.tsx（URL 未匹配时的兜底页）
import { Link } from "react-router";
export default function NotFound() {
  return (
    <main>
      <h1>404 · 页面走丢了</h1>
      <p>你访问的地址不存在。</p>
      <Link to="/">回到首页</Link>
    </main>
  );
}
```

**验证清单：**
- 访问 `/concerts/chicago/999`（不存在）→ 看到友好的 404 页（来自 loader 的 `throw data`）。
- 访问 `/some-random-url` → 看到 NotFound（来自 `path:"*"`）。
- 访问 `/admin/report`（模拟无权）→ 看到 403 页。
- 触发那个 bug loader → 看到「出错了」页；开发环境能看到 stack，`import.meta.env.PROD` 下看不到。

## 🔧 常见坑 / 排错

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 出错直接白屏，没走我的边界 | 该路由及祖先都没有错误边界 | 至少在根路由加 `ErrorBoundary` |
| `error.status` 是 undefined | 错误是 `Error` 实例而非 data 响应 | 先用 `isRouteErrorResponse` 判类型 |
| 把校验错误渲染成整页错误 | 表单校验用了 throw | 校验错误改 `return { errors }` + `useActionData` |
| 子路由出错连父布局一起没了 | 只在根部放了边界 | 给关键子区块单独加边界，缩小爆炸半径 |
| 生产环境泄露了 stack | 直接渲染了 `error.stack` | 用 `import.meta.env.DEV` 包裹技术细节 |
| 未登录跳到错误页而不是登录页 | loader 里 `throw data(401)` 而非 redirect | 未登录用 `return redirect("/login")` |
