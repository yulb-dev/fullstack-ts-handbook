# 第 9 章 · 单元测试（loader / action / 组件）

> 本章目标：**给路由层写单元测试**——把 loader/action 当普通函数直接测，用 `createRoutesStub` 测依赖路由上下文的组件，并建立正确的测试分层策略。
> 对应验收项：⑧-b
> 预计用时：60 分钟

---

## 9.1 为什么 Data Mode 特别好测

Data Mode 的一个隐藏红利：**loader 和 action 就是「接收 `Request`、返回数据 / `Response`」的普通异步函数**，它们拥抱 Web 标准，不依赖 React、不依赖浏览器 DOM。

这意味着：

- **测 loader/action 不需要渲染任何组件**，直接调用函数、断言返回值即可——快、稳、易读。
- 它们的行为在「浏览器 / Node / 测试环境」里完全一致。

而依赖路由上下文的**组件**（用了 `useLoaderData`、`useActionData`、`<Form>`、`<Link>` 等），则需要一个「迷你路由环境」才能渲染——这就是 `createRoutesStub` 的职责。

测试分两层：

| 层次         | 测什么                                         | 工具                                 |
| ------------ | ---------------------------------------------- | ------------------------------------ |
| **纯函数层** | loader / action 的逻辑（返回、redirect、抛错） | 直接 import 调用 + mock 数据层       |
| **组件层**   | 用了路由 hook 的组件、错误边界、表单交互       | `createRoutesStub` + Testing Library |

## 9.3 直接测试 loader（纯函数层）

被测对象是第 3 章的详情页 loader。**关键技巧**：

1. 用 `new Request(...)` 造一个标准请求（含 URL 与查询参数）。
2. 手动传 `params`（模拟路由解析出的动态段）。
3. **mock 数据层**（`src/api.ts`），避免测试依赖真实数据/网络。

```tsx filename=src/routes/concerts/detail.tsx（被测代码，与配套示例工程一致）
import { data } from "react-router";

export async function loader({ request, params }) {
  const concert = await getConcert(params.concertId, {
    signal: request.signal,
  });
  if (!concert) throw data("找不到这场演唱会", { status: 404 });
  return { concert };
}

// 收藏开关：局部提交（由第 5 章的 fetcher.Form 触发），返回结果
export async function action({ request, params }) {
  const fd = await request.formData();
  const favorite = fd.get("favorite") === "true";
  await updateConcert(params.concertId, { favorite });
  return { ok: true, favorite };
}
```

```tsx filename=src/routes/concerts/detail.test.tsx
import { describe, it, expect, vi, beforeEach } from "vitest";

// mock 掉数据层：把「后端」变成可控的假实现
vi.mock("../../api", () => ({
  getConcert: vi.fn(),
  updateConcert: vi.fn(),
}));

import { loader, action } from "./detail";
import * as api from "../../api";

const mockReq = (url: string, init?: RequestInit) => new Request(url, init);

describe("detail loader", () => {
  beforeEach(() => vi.clearAllMocks());

  it("找到数据时返回 concert", async () => {
    vi.mocked(api.getConcert).mockResolvedValue({
      id: "3",
      city: "chicago",
      title: "Jazz Night",
      date: "2026-12-05",
    });

    const result = await loader({
      request: mockReq("http://localhost/concerts/chicago/3"),
      params: { city: "chicago", concertId: "3" },
    });

    expect(api.getConcert).toHaveBeenCalled(); // 确认调用了数据层
    expect(result).toEqual({
      concert: expect.objectContaining({ title: "Jazz Night" }),
    });
  });

  it("数据不存在时抛出 404", async () => {
    vi.mocked(api.getConcert).mockResolvedValue(undefined);

    // loader 里 throw data(..., {status:404}) → 断言它 reject
    await expect(
      loader({
        request: mockReq("http://localhost/concerts/chicago/999"),
        params: { city: "chicago", concertId: "999" },
      }),
    ).rejects.toBeDefined();
    // 若要断言「渲染出 404 UI」，用 9.5 的 createRoutesStub 更直观
  });
});

describe("detail action", () => {
  beforeEach(() => vi.clearAllMocks());

  it("切换收藏：写库并返回结果", async () => {
    vi.mocked(api.updateConcert).mockResolvedValue({
      id: "3",
      city: "chicago",
      title: "Jazz Night",
      date: "2026-12-05",
      favorite: true,
    });

    const res = await action({
      request: mockReq("http://localhost/concerts/chicago/3", {
        method: "POST",
        body: new URLSearchParams({ favorite: "true" }), // request.formData() 可解析
      }),
      params: { city: "chicago", concertId: "3" },
    });

    expect(api.updateConcert).toHaveBeenCalledWith("3", { favorite: true });
    expect(res).toEqual({ ok: true, favorite: true });
  });
});
```

要点回顾：

- **loader/action 无需渲染组件**，直接 `await` 调用、断言返回值。
- **`request.formData()`** 能解析 `URLSearchParams`（表单编码）或 `FormData`（multipart）作为 body。
- **mock 数据层**让测试聚焦「路由逻辑」，不受后端影响。
- 📌 **TypeScript 提示**：`loader`/`action` 的入参类型（`LoaderFunctionArgs`/`ActionFunctionArgs`）含 `request`、`params`、`context` 三个字段。直接调用时若开启严格类型检查，可能要求补齐 `context`——配套示例 `detail.test.tsx` 用一个 `makeArgs` 辅助函数统一构造并做了类型处理。Vitest 默认只转译、不做类型检查，所以上面的简化写法能正常运行。

### 测试 redirect（302 + Location）

`detail` 的 action 不重定向，但登录 action（`login.tsx`）会 `redirect(from)`。**`redirect()` 返回真实的 `Response`**，可直接断言状态码与 `Location` 头：

```ts filename=src/routes/login.test.ts
import { describe, it, expect } from "vitest";
import { action } from "./login";

describe("login action", () => {
  it("登录后 redirect 回来源页（302 + Location）", async () => {
    const request = new Request(
      "http://localhost/login?from=%2Fadmin%2Freport",
      {
        method: "POST",
        body: new URLSearchParams({ role: "admin" }),
      },
    );

    const res = await action({ request });

    expect(res.status).toBe(302);
    expect(res.headers.get("Location")).toBe("/admin/report");
  });
});
```

## 9.4 测试 action 的「校验错误映射」

第 4 章的表单校验 action 返回 `{ ok:false, errors, values }`。这类纯逻辑同样可以直接测：

```ts filename=src/routes/concerts/new.test.ts
import { describe, it, expect } from "vitest";
import { action } from "./new";

const post = (fields: Record<string, string>) =>
  new Request("http://localhost/concerts/new", {
    method: "POST",
    body: new URLSearchParams(fields),
  });

describe("new concert action - validation", () => {
  it("标题太短时返回字段错误", async () => {
    const result = await post({
      city: "chicago",
      title: "ab",
      date: "2026-12-05",
    }).then((request) => action({ request }));

    expect(result.ok).toBe(false);
    expect(result.errors.title).toMatch(/至少 3/);
    expect(result.values).toEqual({
      city: "chicago",
      title: "ab",
      date: "2026-12-05",
    });
  });

  it("日期格式错误时返回字段错误", async () => {
    const result = await action({
      request: post({
        city: "chicago",
        title: "Jazz Night",
        date: "12/05/2026",
      }),
    });
    expect(result.errors.date).toBeDefined();
  });
});
```

> 💡 校验逻辑最好抽成独立纯函数（如 `validateConcert(values)`），既能被 action 复用，也能被单独测试——测试金字塔的底层。

## 9.5 用 createRoutesStub 测试组件（组件层）

当组件用了 `useLoaderData` / `useActionData` / `<Form>` / `useSearchParams` 等**依赖路由上下文**的东西时，直接渲染会报错（缺少 Router context）。`createRoutesStub` 造一个「测试用的迷你路由」。

```tsx
function createRoutesStub(routes, context?) => ReactComponent
```

它接收**类似 Route Object 的数组**（可带 `Component`/`loader`/`action`/`ErrorBoundary`），返回一个组件；渲染时用 `initialEntries` 指定「初始 URL」，内部用 memory router，**会真正执行 loader/action**。

### 官方经典例子：测一个登录表单的错误渲染

```tsx filename=src/components/login-form.tsx
import { Form, useActionData } from "react-router";

export function LoginForm() {
  const actionData = useActionData();
  const errors = actionData?.errors;
  return (
    <Form method="post">
      <label>
        <input type="text" name="username" />
        {errors?.username && <div>{errors.username}</div>}
      </label>
      <label>
        <input type="password" name="password" />
        {errors?.password && <div>{errors.password}</div>}
      </label>
      <button type="submit">Login</button>
    </Form>
  );
}
```

```tsx filename=src/components/login-form.test.tsx
import { createRoutesStub } from "react-router";
import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./login-form";

test("提交后渲染 action 返回的字段错误", async () => {
  const USER_MSG = "Username is required";
  const PASS_MSG = "Password is required";

  // 用 stub 提供一个「假装」的 action，返回我们要的错误
  const Stub = createRoutesStub([
    {
      path: "/login",
      Component: LoginForm,
      action: () => ({ errors: { username: USER_MSG, password: PASS_MSG } }),
    },
  ]);

  render(<Stub initialEntries={["/login"]} />);

  await userEvent.click(screen.getByText("Login"));
  await waitFor(() => screen.findByText(USER_MSG));
  await waitFor(() => screen.findByText(PASS_MSG));
});
```

### 测「loader 数据 → 组件渲染」

```tsx
const Stub = createRoutesStub([
  {
    path: "/concerts/:city",
    Component: ConcertsCity,
    loader: () => ({
      city: "chicago",
      concerts: [
        { id: "3", title: "Jazz Night", city: "chicago", date: "2026-12-05" },
      ],
      q: "",
      sort: "date",
      page: 1,
      totalPages: 1,
    }),
  },
]);

render(<Stub initialEntries={["/concerts/chicago"]} />);
expect(await screen.findByText("Jazz Night")).toBeInTheDocument();
```

### 测「loader 抛错 → 错误边界渲染」（对应第 6 章）

```tsx
import {
  createRoutesStub,
  isRouteErrorResponse,
  useRouteError,
  data,
} from "react-router";

const Stub = createRoutesStub([
  {
    path: "/concerts/:city/:concertId",
    Component: ConcertDetail,
    loader: () => {
      throw data("找不到这场演唱会", { status: 404 });
    },
    ErrorBoundary: () => {
      const error = useRouteError();
      return isRouteErrorResponse(error) ? (
        <div>
          {error.status} {error.data}
        </div>
      ) : (
        <div>未知错误</div>
      );
    },
  },
]);

render(<Stub initialEntries={["/concerts/chicago/999"]} />);
expect(await screen.findByText(/404/)).toBeInTheDocument();
expect(await screen.findByText(/找不到这场演唱会/)).toBeInTheDocument();
```

> 💡 这是断言「404 UI」最直观的方式：让 loader 真的抛 404，走完整条「loader → 错误边界」链路，再断言渲染结果——比在纯函数层去猜抛出的对象形状更贴近真实行为。

### 测「URL 查询参数驱动的组件」（对应第 7 章）

`initialEntries` 支持带查询串，`useSearchParams` 会读到它：

```tsx
const Stub = createRoutesStub([
  {
    path: "/concerts/:city",
    Component: ConcertsCity,
    loader: ({ request }) => {
      const url = new URL(request.url);
      return { q: url.searchParams.get("q") ?? "" /* ... */ };
    },
  },
]);

render(<Stub initialEntries={["/concerts/chicago?q=jazz"]} />);
expect(await screen.findByDisplayValue("jazz")).toBeInTheDocument(); // 搜索框回填
```

## 9.6 测试分层策略（别把所有东西都塞进 stub）

官方对 `createRoutesStub` 有明确的定位建议，务必理解：

- ✅ **适合**：单元测试**可复用组件**——它们依赖路由上下文（`loaderData`/`actionData`/`matches`），但逻辑相对独立（表单、列表项、搜索框、错误边界）。
- ⚠️ **不适合**：直接测试**整条路由链组合出来的「路由组件」**（尤其 Framework Mode 下用 `Route.*` 生成类型的组件）。因为 stub 里你提供的是「假的」loaderData/matches，类型和结构与真实应用不一致，容易产生「类型说谎」的问题。
- 👉 **对「整页/整条路由」的验证，用集成 / E2E 测试**（Playwright、Cypress）跑真实应用更合适。

推荐的分层：

```
        ▲  数量少
        │  E2E（Playwright/Cypress）：跑真实应用，验证「点链接→加载→提交→跳转」整条用户旅程
        │  ────────────────────────────────
        │  组件测试（createRoutesStub）：单个组件 + 假 loader/action
        │  ────────────────────────────────
        │  纯函数测试：loader/action/校验函数，直接调用 + mock 数据层
        ▼  数量多
```

**经验法则**：把**业务逻辑尽量下沉到纯函数与 loader/action**（好测），组件只负责渲染（用 stub 测关键交互），端到端只覆盖少数核心用户旅程（贵、慢，少而精）。

> 📌 **Framework Mode 补充**：若你日后升级到 Framework Mode，Route 组件用 `Route.ComponentProps`/`Route.LoaderArgs` 等生成类型，把它们放进 `createRoutesStub` 会有类型不匹配（`matches` 结构对不上）。官方建议：这类整路由测试走 E2E；若确需单元测试，可用 `@ts-expect-error` 抑制类型错误并清楚注释原因。本教程用 Data Mode，一般不碰这个问题。

## 🔧 常见坑 / 排错

| 现象                                                    | 原因                                    | 解决                                                                 |
| ------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------- |
| 组件测试报 `useLoaderData must be used within a Router` | 直接 render 了组件                      | 用 `createRoutesStub` 包一层再 render                                |
| loader 测试里 `request.formData()` 拿不到值             | body 没按表单编码构造                   | body 用 `new URLSearchParams({...})` 或 `FormData`，method 设为 POST |
| mock 不生效                                             | `vi.mock` 写在了 import 之后 / 路径不对 | `vi.mock` 用工厂函数并置于顶部；确认路径与被测文件里 import 的一致   |
| 断言 404 状态码困难                                     | 直接测「抛出的 data 对象」形状不稳      | 改用 `createRoutesStub` 渲染错误边界后断言 UI                        |
| stub 里 loader 没执行                                   | 路由 path 与 initialEntries 不匹配      | 确认 `initialEntries` 的 URL 能匹配到该 stub 路由                    |
| 把整条路由用 stub 测，类型/结构对不上                   | stub 只适合可复用组件                   | 整路由/整页改用 E2E（Playwright/Cypress）                            |
