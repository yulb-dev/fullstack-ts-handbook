# 第 1 章：为什么需要 Docker 与本地可复现环境

> 本章目标：建立容器化的心智模型——说清「环境漂移」为什么发生、容器与虚拟机的本质区别、Docker 各组件的分工；给出本教程的地图与贯穿项目。
>
> 对应核心概念：**总目标（能将前端静态构建和 Fastify API 打包为可运行镜像，并可靠地管理环境配置）。**

---

## 1.1 一个真实的事故现场

周五下午六点，你合并了最后一个 PR，本地一切正常：

```bash
pnpm dev          # 前端 5173、后端 3000，数据库是你本机装的 Postgres 17
pnpm test         # 全绿
```

部署到测试环境后：

```
Error: connect ECONNREFUSED 127.0.0.1:5432
```

排查一小时后发现三件事叠加：

1. 测试服务器的数据库在**另一台机器**上，`127.0.0.1` 当然连不上——你的配置把「本机」写死了；
2. 服务器上是 **Node 20**，你本地是 Node 24，某个依赖用了 Node 22+ 的 API；
3. 服务器上根本没有装 pnpm，运维用 `npm install` 装的依赖，**没有 lockfile 约束**，装出来的版本树和你本地不一样。

三个问题，一个共同根源：**「应用 + 它依赖的整个环境」没有被当作一个整体来版本化**。代码有 Git，环境没有。

## 1.2 环境漂移：问题比想象中大

「环境」包括：运行时版本（Node）、系统库（glibc/openssl）、包管理器与依赖树、数据库、配置与秘密、启动方式。任何一项在「你的机器 / 同事的机器 / CI / 生产」之间不一致，都可能产生**只在某个环境出现的 bug**。这类 bug 最贵，因为：

- 复现成本高：你要先重建对方的环境；
- 信任被破坏：「在我机器上能跑」成为团队口头禅，意味着没有人能证明「它在任何机器上都能跑」。

路线图阶段 15 的目标就是消灭这句话：**别人可以从仓库按说明构建和运行镜像**——环境本身成为仓库的一部分。

## 1.3 容器 vs 虚拟机：隔离的是什么

|          | 虚拟机（VM）                    | 容器（Container）                            |
| -------- | ------------------------------- | -------------------------------------------- |
| 隔离层级 | 硬件级：每个 VM 有完整 Guest OS | 进程级：共享宿主内核，隔离文件系统/网络/进程 |
| 启动速度 | 分钟级                          | 秒级/毫秒级                                  |
| 体积     | GB 级（整个 OS）                | MB 级（应用 + 最小依赖）                     |
| 隔离强度 | 强（独立内核）                  | 较弱（共享内核，靠 namespace/cgroup）        |
| 适合     | 跑不同 OS、强隔离多租户         | 打包与分发应用、可复现环境                   |

关键认知：**容器不是轻量虚拟机，而是「被隔离和限制的进程」**。你的 Fastify 进程在容器里看到的文件系统、网络、进程列表，都是 Docker 用 Linux namespace 给它「圈」出来的一小块；cgroup 限制它能用多少 CPU/内存。macOS/Windows 上 Docker Desktop 会先起一个 Linux VM，容器跑在那个 VM 里——这也是为什么 Mac 上 Docker 的文件 I/O 比 Linux 慢。

对全栈工程师来说，容器的价值不是「虚拟化」，而是三件事：

1. **打包**：把「应用 + 运行时 + 依赖 + 启动命令」打成一个不可变产物（镜像）；
2. **分发**：镜像推到 registry，任何机器拉下来跑出的环境完全一致；
3. **编排**：用 Compose 把「API + 数据库 + 前端」声明成一份可版本化的 YAML。

## 1.4 Docker 的组件地图

```
Dockerfile ──build──> 镜像（image）──push──> registry（如 Docker Hub）
                          │
                        run（创建 + 启动）
                          ▼
                       容器（container）= 镜像 + 可写层 + 隔离的进程
                          │
              ┌───────────┼────────────┐
           network     volume       环境变量
          （容器互联） （数据持久化） （运行时配置）
```

- **Dockerfile**：构建镜像的「配方」，文本文件，进 Git；
- **镜像**：只读模板，由一层层 layer 叠成；
- **容器**：镜像的运行实例，顶部加一个可写层；
- **registry**：镜像的仓库（Docker Hub、GHCR、公司私有 registry）；
- **Compose**：多容器应用的声明式编排工具，`compose.yaml` 进 Git。

这些概念第 2、3 章会逐个上手，第 4 章起写自己的 Dockerfile。

## 1.5 本教程的贯穿项目与终点

贯穿项目是 **Workboard**（阶段 14 的 monorepo 骨架）。本教程结束时，你将拥有：

```bash
# 任何人、任何装了 Docker 的机器，clone 后：
cp .env.example .env
docker compose up --build -d

curl http://localhost:3000/health/ready   # {"status":"ready"}  ← API 连上了容器里的 Postgres
open http://localhost:8080                # nginx 托管的前端，能创建任务
docker compose down                     # 优雅停止，数据卷保留
```

并且你能回答三个审计问题：**镜像里有没有秘密？进程是不是非 root？停止时是否优雅？**——这正是路线图阶段 15 的三条通过标准。

## 1.6 常见坑（认知层面）

| 误区                               | 正确认知                                                                   |
| ---------------------------------- | -------------------------------------------------------------------------- |
| 容器 = 轻量虚拟机                  | 容器是共享内核的隔离进程；Mac/Windows 上跑在 Docker Desktop 的 Linux VM 里 |
| 把容器当持久服务器，进去改配置     | 容器应「用完即毁」（ephemeral）；配置走环境变量，数据走 volume             |
| 镜像能跑就算生产化                 | 还要非 root、信号处理、健康检查、秘密注入、可重建性（路线图高频误区）      |
| 开发环境怎么跑，生产镜像就怎么打包 | dev server/热更新/devDependencies 都不该进生产镜像（第 6、11 章）          |
