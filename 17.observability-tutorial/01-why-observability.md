# 第 1 章：为什么需要可观测性

> 本章目标：把「出错了」升级成四个可回答的问题；分清日志、指标、追踪三支柱；给出本教程的排障闭环地图。
>
> 对应核心概念：**③ 日志、指标、追踪的区别。**

---

## 1.1 深夜告警的四个问题

线上「创建任务失败」。一个没有可观测性的团队会这样对话：

```
客服：用户说创建任务失败了。
后端：什么时候？哪个账号？报什么错？
客服：不知道，用户就说了「失败」。
后端：我翻翻日志……日志里全是 Error: something went wrong，分不清是哪次。
前端：我这边 Sentry 有个错，但跟后端对不上。
两小时后：还在猜。
```

可观测性（Observability）的目标，是让这四个问题**有确定答案**：

| 问题           | 靠什么回答                         |
| -------------- | ---------------------------------- |
| 哪里出错？     | Sentry 错误事件（堆栈 + release）  |
| 影响谁？       | requestId + 用户/租户标签（脱敏）  |
| 经过哪些服务？ | OpenTelemetry trace（因果链）      |
| 如何复现？     | 结构化日志 + trace + envelope 串联 |

## 1.2 三支柱：各自回答什么

| 支柱         | 是什么                 | 回答的问题                   | 例子                        |
| ------------ | ---------------------- | ---------------------------- | --------------------------- |
| 日志 Logs    | 离散事件的细节记录     | 「这次请求具体发生了什么」   | 一条含 requestId 的错误日志 |
| 指标 Metrics | 聚合的数值趋势         | 「整体健康吗、趋势如何」     | 错误率、p99 延迟、QPS       |
| 追踪 Traces  | 一次请求跨服务的因果链 | 「时间花在哪、经过哪些环节」 | server span → DB span       |

三者互补，缺一不可：

- 只有日志：知道单次细节，但不知道整体趋势（错误率涨了没？）；
- 只有指标：知道趋势异常，但定位不到具体请求；
- 只有 trace：知道因果链，但缺少业务语义细节。

**本教程聚焦日志 + 追踪 + 错误监控**（Sentry），指标作为思路在第 10 章介绍（SLO/错误率/延迟）。这与路线图阶段 17 的范围一致。

## 1.3 可观测性 vs 监控

- **监控（Monitoring）**：预先定义「什么算坏」（阈值告警），回答已知问题；
- **可观测性（Observability）**：能从系统外部输出推断内部状态，回答**未预定义**的问题。

高基数维度（requestId、userId、taskId）是日志/trace 的强项，却是传统指标系统的弱项（维度爆炸）。这就是为什么排障要靠日志 + trace，而不是只盯仪表盘。

## 1.4 本教程的闭环

```
前端异常 ──Sentry──> 错误事件（release/env + requestId tag）
                         │ requestId
后端请求 ──Pino──> 结构化日志（reqId + trace_id + span_id）
                         │ trace_id
        ──OTel──> trace（http server span → task.create span → pg span）
                         │
                  三者由 requestId / trace_id 串联 → 一次故障可全链路定位
```

贯穿项目 Workboard 的「创建任务」链路会被完整 instrument。第 11 章用一次故意注入的故障（`FAIL_DB`）演练从 UI 到 DB 的定位。

## 1.5 常见坑（认知层面）

| 误区                      | 正确认知                                                    |
| ------------------------- | ----------------------------------------------------------- |
| 装了 Sentry/OTel 就能排障 | 还要 requestId/trace 能关联，并有演练证明（路线图高频误区） |
| 日志越多越好              | 无结构、无关联的日志是噪声；要可查询字段 + 脱敏             |
| trace 全量记录            | 高吞吐下成本爆炸；要采样策略（第 10 章）                    |
| 三支柱可以互相替代        | 各自回答不同问题，互补而非替代                              |
