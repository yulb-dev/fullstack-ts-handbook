# 第 1 章：可观测性是什么

> 本章目标：在接任何工具之前，先搞懂——可观测性是什么、日志/指标/追踪是什么、Sentry 和 OpenTelemetry 各是干什么的。本章假设你**只在控制台打过 `console.log`，从没接过监控工具**。
>
> 学完本章你能：用大白话解释可观测性；分清日志、指标、追踪；说清 Sentry 和 OTel 各自的角色。

---

## 1.1 一句话：可观测性是什么

**可观测性（Observability）= 不用打开应用内部，就能从它「对外吐出的信息」推断出里面发生了什么的能力。**

听起来抽象？换个说法：

> 你的应用上线后，用户说「坏了」。你不在用户电脑前，也不能钻进服务器里看。你只能靠应用**主动留下的线索**——日志、错误报告、请求轨迹——来还原「到底发生了什么」。可观测性就是「让这些线索足够好用」这件事。

### 医生看病类比

病人（应用）说「我不舒服」。医生（你）不能直接看穿身体，靠的是：

- **病历**（日志）：什么时候、做了什么、当时什么反应——一次次事件的细节；
- **体检报告**（指标）：体温、血压、心率——整体的数值趋势；
- **行程轨迹**（追踪）：这次不舒服，经过了哪些环节、每个环节花了多久——一次过程的因果链。

三者结合，才能从「不舒服」定位到「具体哪个器官、什么原因」。可观测性就是给应用建立这套「病历 + 体检 + 轨迹」。

## 1.2 三支柱：日志、指标、追踪

这是可观测性的三种基本数据，**各自回答不同的问题**：

| 支柱         | 是什么                     | 回答的问题                   | 生活类比 |
| ------------ | -------------------------- | ---------------------------- | -------- |
| 日志 Logs    | 一条条事件的细节记录       | 「这次请求具体发生了什么」   | 病历     |
| 指标 Metrics | 聚合的数值趋势             | 「整体健康吗、趋势如何」     | 体检报告 |
| 追踪 Traces  | 一次请求经过各环节的因果链 | 「时间花在哪、经过哪些环节」 | 行程轨迹 |

举个具体例子，「创建任务」这个请求：

- **日志**：`18:00:01 req-2 创建任务失败，错误码 INTERNAL_ERROR`（一条细节）；
- **指标**：「过去 5 分钟创建任务的错误率从 0.1% 涨到 30%」（一个趋势）；
- **追踪**：`请求进来 → 校验参数(2ms) → 查权限(5ms) → 写数据库(超时!)`（一条因果链，看出卡在数据库）。

**三者互补，缺一不可**：只有日志，不知道整体趋势；只有指标，定位不到具体请求；只有追踪，缺少业务细节。

> 本教程聚焦**日志 + 追踪 + 错误监控**；指标作为思路在第 10 章介绍。这与路线图阶段 17 的范围一致。

## 1.3 Sentry 是什么

**Sentry 是一个「错误收集与告警平台」。** 你在应用里装一个 SDK，它自动捕获异常，发送到 Sentry 网站，聚合成可搜索、可告警的「问题（issue）」。

它帮你回答：

- **哪里出错**：哪个文件、哪一行、什么堆栈；
- **从哪个版本开始**：release 标识，定位是哪次发布引入的回归；
- **影响多大**：发生了多少次、影响多少用户。

类比：Sentry 像应用的「**急诊科 + 病例归档**」——每次出错自动挂号、按病症归类、统计发病率。第 4~6 章接入它。

## 1.4 OpenTelemetry 是什么

**OpenTelemetry（简称 OTel）是一套「生成和收集追踪数据的标准 + 工具」。** 它定义「一次请求该怎么被记录成一棵因果树」，提供各语言的 SDK 和自动插桩，把数据送到任意后端（Jaeger、Tempo、云厂商）。

它帮你回答：

- **经过哪些环节**：一次请求从 HTTP 进来，到业务逻辑，到数据库，每一段；
- **时间花在哪**：每段耗时，一眼看出慢在哪。

类比：OTel 像给请求装上「**行程记录仪**」——自动记录它经过的每一站和停留时间。第 7~8 章接入它。

**关键区别**：Sentry 主攻「错误」，OTel 主攻「追踪」。两者能配合，但要分工明确，否则同一个请求被记录两遍（第 9 章专门讲）。

## 1.5 为什么需要它：深夜告警的四个问题

理解了「是什么」，再看「为什么」。没有可观测性时，线上「创建任务失败」会这样：

```
客服：用户说创建任务失败了。
后端：什么时候？哪个账号？报什么错？
客服：不知道，用户就说了「失败」。
后端：翻日志……全是 Error: something went wrong，分不清是哪次。
前端：我这边有个错，但跟后端对不上。
两小时后：还在猜。
```

可观测性的目标，是让这四个问题**有确定答案**：

| 问题           | 靠什么回答                        |
| -------------- | --------------------------------- |
| 哪里出错？     | Sentry 错误事件（堆栈 + 版本）    |
| 影响谁？       | requestId + 用户/租户标签（脱敏） |
| 经过哪些服务？ | OTel 追踪（因果链）               |
| 如何复现？     | 日志 + 追踪 + 错误信息串联        |

## 1.6 可观测性 vs 监控（一个常见混淆）

- **监控（Monitoring）**：预先定义「什么算坏」（如错误率 > 1% 就告警），回答**已知**问题；
- **可观测性**：能从外部输出推断内部状态，回答**没预定义过**的问题（「为什么这个特定用户失败？」）。

高基数线索（某个 requestId、某个 userId）是日志/追踪的强项，却是传统指标仪表盘的弱项。所以排障靠日志 + 追踪，而不是只盯仪表盘。

## 1.7 本教程的闭环（地图）

贯穿项目 **Workboard**。我们会把「创建任务」这条链路完整接上：

```
前端异常 ──Sentry──> 错误事件（带 requestId）
后端请求 ──日志──> 结构化日志（带 requestId + trace_id）
        ──OTel──> 追踪（请求 span → 业务 span → 数据库 span）
三者由 requestId / trace_id 串联 → 一次故障可全链路定位（第 11 章演练）
```

两条红线贯穿全程：**隐私脱敏**（密码/token 不进遥测）与**避免重复记录**（Sentry 管错误、OTel 管追踪）。

## 1.8 常见误区

| 误区                      | 正确认知                                               |
| ------------------------- | ------------------------------------------------------ |
| 装了 Sentry/OTel 就能排障 | 还要 requestId/trace 能关联，并演练证明（第 9、11 章） |
| 日志越多越好              | 无结构、无关联的日志是噪声；要可查询 + 脱敏            |
| 追踪全量记录              | 高吞吐下成本爆炸；要采样（第 10 章）                   |
| 三支柱可以互相替代        | 各答不同问题，互补而非替代                             |
