# 第 1 章：CI/CD 与 GitHub Actions 是什么

> 本章目标：在写任何 workflow 之前，先搞懂——CI/CD 是什么、GitHub Actions 是什么、为什么需要它。本章假设你**只在 GitHub 上托管过代码，从没写过自动化流水线**。
>
> 学完本章你能：用大白话解释 CI 和 CD；说清 GitHub Actions 是干什么的；认出 workflow / job / step 这三个最基本的词。

---

## 1.1 先从两个缩写说起

**CI = Continuous Integration（持续集成）**：每次有人改代码，就**自动**把大家的改动合在一起检查一遍——能不能编译、测试过不过、风格对不对。坏了立刻知道，而不是攒到上线前才发现。

**CD = Continuous Delivery / Deployment（持续交付 / 持续部署）**：检查通过的代码，**自动**打包成可发布的产物（交付），甚至自动部署上线（部署）。

一句话：**CI 管「代码是不是好的」，CD 管「把好的代码送上线」。**

### 质检流水线类比

把软件团队想象成一家工厂：

- 工人（开发者）不断做出零件（提交代码）；
- **CI 是质检员**：每个零件送来都自动过一遍检测（编译、测试、lint），不合格立刻退回；
- **CD 是打包发货线**：合格零件自动装箱（构建产物）、贴标签（版本号）、发货（部署）。

没有质检员，不合格零件混进成品，客户（用户）才发现坏了。没有自动发货线，靠人工搬运，慢且容易发错货。

## 1.2 GitHub Actions 是什么

**GitHub Actions 是 GitHub 内置的「自动化机器人」：你用一份 YAML 文件告诉它「什么时候、做什么」，它就照做。**

- 「什么时候」= 触发事件：有人提 PR、代码 push 到 main、手动点按钮、定时……
- 「做什么」= 一系列步骤：拉代码、装依赖、跑测试、构建、部署……

这份 YAML 叫 **workflow（工作流）**，放在仓库的 `.github/workflows/` 目录里。它本身就是代码——进 Git、能被评审、能版本化。

### 一个最小的画面

```yaml
on: pull_request # 什么时候：有人提 PR
jobs:
  check: # 做什么：一个名叫 check 的工作
    runs-on: ubuntu-latest # 在哪做：GitHub 提供的一台临时 Linux 机器
    steps:
      - uses: actions/checkout@v7 # 第一步：把代码拉到机器上
      - run: pnpm test # 第二步：跑测试
```

翻译成人话：「**每当有人提 PR，GitHub 就开一台干净的 Linux 机器，拉下代码，跑一遍测试。**」这就是一个 CI。

## 1.3 三个最基本的词

先建立直觉，第 2、4 章会精确展开：

| 词       | 是什么                                 | 类比                 |
| -------- | -------------------------------------- | -------------------- |
| workflow | 一份 YAML，定义一整套自动化            | 一张「工序单」       |
| job      | workflow 里的一块工作，跑在一台机器上  | 一道「工序」         |
| step     | job 里的一步（用现成 action 或跑命令） | 工序里的「一个动作」 |

还有两个词后面会用到：**runner**（执行 job 的那台机器）、**event**（触发 workflow 的事件）。

## 1.4 为什么需要它：人工流程的事故

理解了「是什么」，再看「为什么」。没有 CI/CD 的团队日常：

```
周一：A 本地「应该没问题」就合并了 → main 红了，全组 pull 下来都是坏的
周二：B 改了依赖没锁版本 → CI 和本地装出不同的库 → 「CI 过了但我本地挂了」
周三：运维手动 scp 了一个本地 build 的包上线 → 线上代码不在任何 commit 里
周四：线上出 bug，问「这是哪个版本？」→ 没人答得上来
周五：回滚？回滚到哪个包？还在吗？→ 靠记忆和运气
```

共同根源：**代码的正确性、构建的可复现性、部署的可追溯性，都没有自动化机制保证**。CI/CD 就是把这三件事变成「自动 + 可审计」：

- **可审计**：哪个 commit、用什么工具链、跑了哪些检查、结果如何，全程有记录；
- **最小权限**：自动化机器人只拿它需要的权限，不被滥用；
- **失败可定位**：坏了能立刻看到是哪一步、为什么。

这三个词正是本教程的主线。

## 1.5 为什么选 GitHub Actions

- 和仓库同平台：PR、分支保护、环境审批、secrets 原生联动；
- workflow 是 YAML，进 Git，流水线本身也被评审；
- 托管 runner 每次都是干净机器——「换台机器也能跑」的最严格检验。

代价也要知道：私有仓库免费额度有限；自己托管 runner 有安全风险（第 7 章）；YAML 语法有学习曲线——本教程帮你拆平。

## 1.6 本教程的三层流水线（地图）

贯穿项目 **Workboard**。我们会搭三条 workflow，权限各不相同：

```
提 PR ────> ci.yml      质检：format / lint / typecheck / test / build，全绿才能合并
合并 main ─> main.yml   复检：集成测试 + 真实浏览器 E2E，失败留下报告
手动部署 ──> deploy.yml 发货：受保护环境 + 人工审批 + 版本标识 + 健康验证 + 可回滚
```

**PR 质检永远碰不到部署的秘密**——两条权限链分开，这是安全的关键（第 7、9 章）。

## 1.7 常见误区

| 误区                              | 正确认知                                              |
| --------------------------------- | ----------------------------------------------------- |
| CI 过了 = 代码没问题              | CI 只证明「声明的检查过了」；检查要覆盖失败路径       |
| 部署就是跑个脚本                  | 部署是「版本标识 + 审批 + 健康验证 + 回滚」的完整流程 |
| GitHub Actions 很复杂，新手碰不了 | 最小 workflow 就几行（1.2），本教程从那里起步         |
| 内部仓库不用管安全                | 权限设计是习惯问题，fork/注入的坑在私有仓一样致命     |
