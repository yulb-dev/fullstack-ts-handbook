# 第 1 章：为什么需要 CI/CD

> 本章目标：建立「门禁即证据、部署即流程」的心智模型；说清人工合并/人工部署的事故模式；给出本教程的三层流水线地图。
>
> 对应核心概念：**总目标（搭建从提交验证到部署的自动化门禁，做到可审计、最小权限、失败可定位）。**

---

## 1.1 没有门禁的团队日常

```
周一：A 合并了 PR，本地测试「应该没问题」→ main 红了，全组 pull 下来都是坏的
周二：B 修复时顺手改了 lockfile，CI 没锁版本，装出另一棵依赖树 → 「CI 过了但我本地挂了」
周三：运维手动部署，scp 了一个本地 build 的 dist → 线上跑的代码不在任何 commit 里
周四：线上出 bug，问「这是哪个版本？」→ 没有人答得上来
周五：回滚？回滚到哪个包？那个包还在吗？→ 靠记忆和运气
```

每一件事单独看都是「小疏忽」，合起来就是**没有工程证据链**：代码的正确性、构建的可复现性、部署的可追溯性，都没有自动化机制保证。

## 1.2 CI/CD 的三个层次

| 层次           | 含义                                 | 本教程产出                |
| -------------- | ------------------------------------ | ------------------------- |
| CI（持续集成） | 每次变更都自动验证，坏了立刻知道     | PR 门禁 + main 验证       |
| CD（持续交付） | 验证通过的产物随时**可以**部署       | 带版本标识的镜像推上 GHCR |
| CD（持续部署） | 验证通过后自动**部署**（通常带审批） | 受保护环境的部署 job      |

关键认知：**CI 的产物不是「绿灯」，而是证据**——哪个 commit、用什么工具链、跑了哪些检查、结果如何，全部可审计。路线图阶段 16 的「可审计、最小权限、失败可定位」三个形容词，分别对应：证据链、权限设计、诊断产物。

## 1.3 为什么是 GitHub Actions

- 与仓库同平台：PR、分支保护、environment、secrets 原生联动；
- workflow 是 YAML，进 Git，**流水线本身也被版本化与评审**；
- 托管 runner 每次都是干净 VM——「全新机器可复现」的最严格检验场（阶段 14 的目标 A 在这里闭环）。

代价与边界也要知道：私有仓库免费额度有限；self-hosted runner 有持久化污染风险（第 7 章）；workflow 语法有学习曲线——正是本教程要拆平的。

## 1.4 本教程的三层流水线

```
pull_request ──> ci.yml     quality: format → lint → typecheck → test → build
                                │ 全绿 + 评审通过
                                ▼
push main ─────> main.yml   integration ──> e2e（生产构建 + 浏览器）
                                │ 失败上传 trace/报告
                                ▼
workflow_dispatch ──> deploy.yml  build-and-push（GHCR, tag=sha）
                                       └─> deploy（production 环境审批 + OIDC + 健康验证）
```

三条 workflow **权限各不相同**：PR 只读、main 只读、部署才有 packages/id-token 写权限——「部署权限和 pull_request 的权限应分开设计」（路线图原话）从第一天就落实。

## 1.5 常见坑（认知层面）

| 误区                     | 正确认知                                                       |
| ------------------------ | -------------------------------------------------------------- |
| CI 过了 = 代码没问题     | CI 只证明「声明的检查过了」；检查本身要覆盖失败路径（阶段 12） |
| 缓存命中 = 构建正确      | 缓存只加速；正确性由 frozen lockfile + 测试保证（第 5 章）     |
| 部署就是跑个脚本         | 部署是「版本标识 + 审批 + 健康验证 + 回滚」的完整流程          |
| 内部仓库不用管 fork 安全 | 权限设计是习惯问题；pull_request_target 的坑在私有仓一样致命   |
