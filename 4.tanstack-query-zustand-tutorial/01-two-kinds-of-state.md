# 第 1 章：两种状态——先建立正确的心智模型

> 返回目录：[README](./README.md) | 下一章：[第 2 章 环境搭建：跑通第一个请求](./02-setup-first-request.md)

这一章没有一行需要安装的代码，却是**全书最重要的一章**。如果你只记住一件事，请记住这句话：

> **前端应用里的「状态」不是一种东西，而是两种本质不同的东西。把它们当成一种来管，是绝大多数数据 bug 和糟糕体验的根源。**

TanStack Query 官方文档开篇就在强调这一点：传统状态管理库擅长处理**客户端状态**，但处理**异步/服务端状态**时非常吃力，因为「服务端状态完全是另一回事」。本章就把这件「另一回事」讲透。

## 1.1 什么是「状态」，为什么它会让人头疼

「状态（state）」就是**应用在某个时刻的数据快照**，界面是这份数据的函数：`UI = f(state)`。数据变了，界面就该跟着变。

React 自带的 `useState` 足以应付「一个组件内部、同步、临时」的数据，比如一个输入框的值：

```tsx
function SearchBox() {
  const [keyword, setKeyword] = useState('')
  return <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />
}
```

这里 `keyword` 的「真相」就在浏览器内存里，你改它，它立刻变，没有第二个来源，也不会「过期」。这类数据很简单。

麻烦从两个方向同时到来：

1. **数据要跨组件共享**——于是有了 props 层层传递（prop drilling）、Context、Redux、Zustand 这些「全局状态」方案；
2. **数据来自服务器**——于是有了 `useEffect + fetch`、loading、error、缓存、重复请求、数据过期……

新手常犯的错，是用**同一套工具**（比如 Redux，或者一个大 Context）去同时解决这两件事。而这两件事的性质天差地别。下面分别看清它们。

## 1.2 客户端状态（Client State / UI State）

**定义**：数据的「唯一真相」就在你当前的浏览器里，**同步、即时、只属于当前用户、不来自也不需要和服务器对齐**。

典型例子：

| 数据 | 说明 |
| --- | --- |
| 侧边栏是否展开 | 纯 UI，刷新页面丢了也无所谓（或存 localStorage） |
| 主题（深色/浅色） | 用户偏好，通常持久化到本地 |
| 当前选中的筛选/排序/标签页 | 视图控制，和「数据本身」无关 |
| 弹窗（Modal）是否打开 | 临时 UI 状态 |
| 表单草稿、多步向导的当前步 | 用户还没提交的输入 |
| 复制成功的「已复制」提示 | 一闪而过的 UI 反馈 |

它的特征：

- **你拥有它**：没有其他来源会「偷偷」改它，你 `set` 了就是它了；
- **同步**：改完立刻生效，不涉及网络、不涉及等待；
- **不需要缓存/失效**：它本身就是真相，不存在「过期」；
- **通常很小**：几个布尔值、几个字符串、一个枚举。

客户端状态的管理诉求很朴素：**能跨组件读写、改动时精准地只重渲染用到它的组件、必要时持久化**。这正是 Zustand 的主场——一个轻量、无 Provider、基于 selector 细粒度订阅的 store。第 9~11 章会把它讲透。

## 1.3 服务端状态（Server State）：完全是另一回事

**定义**：数据的「唯一真相」在**远端服务器**上（数据库、别人的应用、甚至同一个应用的其它客户端）。你手里拿到的，**永远只是它某个时间点的一份缓存副本**。

TanStack Query 官方文档精准地列出了服务端状态的四个本质特征，请逐条体会：

1. **它被持久化在一个你不控制、也不拥有的远端位置**；
2. **它需要异步 API 来获取和更新**（获取要等，更新也要等）；
3. **它意味着「共享所有权」——别人可以在你不知情的情况下改动它**；
4. **如果你不小心，它会在你的应用里「过期」（变得和服务器不一致）**。

把这四条翻译成日常场景，你就懂了为什么它难：

- 你打开任务列表，看到的是「你发起请求那一刻」的快照。**下一秒同事可能就新增了一条任务**，而你界面上没有——数据已经「过期」了，但你不知道。
- 你点了「删除」，请求发出去了，但**要等 300ms 才知道成功还是失败**。这 300ms 里界面该显示什么？删除失败要不要把条目「变回来」？
- 两个组件同时需要同一份用户信息，**难道要发两次请求**？
- 用户在页面间来回切换，**每次都要重新 loading 转圈**吗？能不能记住上次的数据先显示，同时后台悄悄更新？

一旦你承认「我手里的只是缓存副本」，一连串新问题就冒出来了（同样是官方文档列出的）：

> 缓存（可能是编程里最难的事之一）、把对同一数据的多个请求去重成一个、在后台更新过期数据、知道数据什么时候过期、尽快把更新反映到界面、分页与懒加载等性能优化、服务端状态的内存管理与垃圾回收、用结构共享来记忆化查询结果……

**这些问题，用 `useState` 或 Redux 去手搓，代码量和 bug 量都会爆炸。** 而它们又高度模式化——每个请求都要处理 loading/error/success、缓存、重试、失效。于是就有了 TanStack Query：它把这些模式封装成声明式的 `useQuery` / `useMutation`，让你「描述数据依赖」而不是「手写状态机」。

## 1.4 关键对比：为什么它们是两种东西

把两类状态并排放，差异一目了然：

| 维度 | 客户端状态（Zustand） | 服务端状态（TanStack Query） |
| --- | --- | --- |
| 真相来源 | 浏览器本地，你独占 | 远端服务器，多方共享 |
| 读写方式 | 同步，立刻生效 | 异步，要等网络 |
| 会不会「过期」 | 不会，它就是真相 | 会，随时可能被别人改动 |
| 需要缓存吗 | 不需要 | 需要，且要管新鲜度/回收 |
| 需要失效/重新拉取吗 | 不需要 | 需要（invalidate / refetch） |
| 需要重试、错误态吗 | 一般不需要 | 需要（网络会失败） |
| 需要 loading 态吗 | 不需要 | 需要（pending / fetching） |
| 典型数据量 | 极小（几个值） | 可能很大（列表、分页数据） |
| 持久化 | 常见（localStorage） | 一般不手动持久化，靠缓存机制 |
| 正确的工具 | Zustand | TanStack Query |

看这张表你会发现：**服务端状态需要一整套客户端状态根本不需要的机制**（loading、error、缓存、失效、重试、乐观更新、去重）。如果你用 Zustand 存服务端数据，这些机制你全得自己手写；如果你用 TanStack Query 存 UI 状态（比如弹窗开关），则是杀鸡用牛刀且语义错位——它没有「服务器」可以对齐。

## 1.5 为什么绝不能把它们混成一种状态

这是本章、也是全书的核心论点。混合管理会带来四类具体问题：

### 问题一：用错了抽象，代码量和 bug 量翻倍

把服务端数据塞进 Zustand store，你就得**自己实现**：loading 标志、error 字段、请求去重、缓存过期、窗口聚焦刷新、重试、乐观更新回滚……这些 TanStack Query 开箱即有。手写等于重新发明一个更差的 TanStack Query。

```ts
// ❌ 反模式：把服务端状态硬塞进客户端状态库
const useTaskStore = create((set) => ({
  tasks: [],
  isLoading: false,      // 你得自己维护
  error: null,           // 你得自己维护
  lastFetchedAt: 0,      // 你还得自己算"是否过期"
  fetchTasks: async () => {
    set({ isLoading: true, error: null })
    try {
      const res = await fetch('/api/tasks')
      set({ tasks: await res.json(), isLoading: false, lastFetchedAt: Date.now() })
    } catch (e) {
      set({ error: e, isLoading: false })
    }
  },
  // 去重呢？窗口聚焦刷新呢？失效呢？重试呢？……全得自己写
}))
```

```ts
// ✅ 正确：服务端状态交给 TanStack Query，上面那一大堆它全包了
const { data, isPending, isError, error } = useQuery({
  queryKey: ['tasks'],
  queryFn: () => fetch('/api/tasks').then((r) => r.json()),
})
```

### 问题二：制造「两份真相」，数据迟早打架

如果任务列表既在 TanStack Query 的缓存里，又被复制进一个 Zustand store，你就有了**两份可能不一致的副本**。哪份是对的？什么时候同步？一旦某处只更新了其中一份，界面就会显示矛盾的数据。这类 bug 极难排查。第 12 章会把「不要把服务端数据复制进 Zustand」列为一条铁律。

### 问题三：让「客户端状态」背上了不该有的异步复杂度

反过来，如果你试图用一个「万能 store」把 UI 状态和数据获取混在一起，store 里就会充斥着 `isLoading`、`isSaving`、缓存时间戳、请求函数……本该轻快的 UI 状态管理变得沉重、难以测试、难以推理。

### 问题四：性能优化的手段完全不同

- 客户端状态的优化重点是**细粒度订阅**（只让用到某个字段的组件重渲染）——Zustand 的 selector 天生为此设计；
- 服务端状态的优化重点是**缓存复用、请求去重、后台刷新、结构共享、引用稳定性**——TanStack Query 天生为此设计。

用一套工具同时追求两种优化，往往两头不讨好。

## 1.6 正确的心智模型：状态分层

把应用的数据想象成分层，每层用最合适的工具：

```
┌─────────────────────────────────────────────────────────┐
│  服务端状态（异步、远端、会过期）                           │
│  → TanStack Query：useQuery / useMutation                 │
│    例：任务列表、任务详情、评论、用户资料                    │
├─────────────────────────────────────────────────────────┤
│  客户端状态（同步、本地、UI 控制）                          │
│  → Zustand：create / selector                             │
│    例：筛选条件、主题、侧边栏、弹窗开关、表单草稿            │
├─────────────────────────────────────────────────────────┤
│  组件局部状态（同步、临时、不跨组件）                       │
│  → React useState / useReducer                           │
│    例：单个输入框的值、hover 高亮                          │
└─────────────────────────────────────────────────────────┘
```

一个判断数据归属的**决策流程**，请背下来：

```
这份数据的"真相"在服务器上吗？（会通过网络获取/修改，可能被别人改动）
   ├── 是  →  服务端状态  →  TanStack Query（useQuery / useMutation）
   └── 否
        └── 它需要被多个（较远的）组件共享，或需要持久化吗？
             ├── 是  →  客户端全局状态  →  Zustand
             └── 否  →  组件局部状态  →  React useState
```

### 一个容易混淆的边界情况

「筛选条件」到底算哪种？答案是**看它本身，而不是看它影响什么**：

- `filter = 'done'`（当前选中「已完成」）——这是**客户端状态**，它只是 UI 的一个选择，放 Zustand（或局部 state）。
- 「筛选后的任务列表」——这是**服务端状态**，因为它是从服务器按 `filter` 查出来的数据，用 TanStack Query 获取，并把 `filter` **放进 query key**（第 3、7 章详述）。

看到没？同一个「筛选」功能，**「用户选了什么」归 Zustand，「按这个选择查出来的数据」归 TanStack Query**。这就是分工的精髓：它们协作，但各自管理各自擅长的那部分。这个模式会在 TaskFlow 项目里反复出现。

## 1.7 工具选型速览

| 需求 | 首选 | 为什么 |
| --- | --- | --- |
| 从 API 获取数据并缓存 | TanStack Query | 内建缓存、去重、失效、重试、乐观更新 |
| 提交/修改服务器数据 | TanStack Query（useMutation） | 生命周期回调 + 自动失效相关缓存 |
| 跨组件共享的 UI 状态 | Zustand | 轻量、无 Provider、细粒度订阅 |
| 需要持久化的用户偏好 | Zustand + persist | 一行中间件搞定 localStorage |
| 单个组件的临时状态 | React useState | 最简单，不必引入外部库 |
| 表单 | React Hook Form 等 | 表单是特化领域，用专门工具 |

> **常见疑问：Zustand 和 TanStack Query 会打架吗？** 完全不会，它们是互补的。一个真实项目里，两者常常同时存在：Zustand 管「用户把界面调成了什么样」，TanStack Query 管「服务器上的数据现在是什么样」。本教程后半段（第 12、13 章）会演示它们如何优雅协作。

> **常见疑问：那我到底还需不需要 Redux？** 如果你的「全局状态」里大部分其实是服务端数据，那么引入 TanStack Query 后，你会发现需要 Redux/Zustand 管的东西**急剧减少**——很多项目最后只剩一点点 UI 状态需要全局管理。这正是 TanStack Query 维护者那篇著名文章 *React Query as a State Manager* 的核心观点。
