# 第 1 章：为什么要测试，测试什么

> 本章不写一行测试代码。它解决的是更重要的问题：当你面对一个功能，**应该用测试证明什么、在哪一层证明、付出多少成本**。后面所有章节的具体技术，都是为这里的判断服务的。

## 1.1 测试验证的是「可观察的承诺」，不是代码本身

新手最常见的误解是：测试 = 把代码跑一遍，确认它没报错。这样写出来的测试往往长这样：

```ts
// 反例：这只证明「代码能执行」，不证明「行为正确」
test("createTask works", async () => {
  const service = createTaskService({ repo, notifier });
  await service.createTask(member, { title: "写周报" });
  // 没有任何断言 —— 只要不抛错就算过
});
```

正确的思维是：**每个函数、组件、接口都对使用者做出了若干「承诺」（contract），测试的职责是逐条验证这些承诺**。

以 TaskDesk Lite 的 `parsePagination`（[example/src/domain/pagination.ts](./example/src/domain/pagination.ts)）为例，它的承诺清单是：

1. 不传参数时，返回第 1 页、每页 20 条；
2. 查询串里的字符串数字（`"3"`）会被正确转成数字；
3. `page` 小于 1、`pageSize` 大于 100、非整数、非数字——统统拒绝（抛 `ZodError`）；
4. `offset` 永远等于 `(page - 1) * pageSize`。

每一条承诺对应至少一个断言。测试写完后，这个函数的行为就被「钉住」了：将来任何人改动它，只要破坏了其中任何一条承诺，测试立刻变红。这就是路线图里说的「能用测试快速定位回归」。

反过来，判断一个测试有没有价值的标准也很简单：**把这个测试的所有断言删掉，它还剩下什么？** 如果答案是「什么都没验证」，那这个测试只是在制造虚假的安全感。

### 测试的三重回报

- **回归防护**：改 A 坏 B 时立刻报警，这是最直接的价值。
- **设计反馈**：难以测试的代码，通常是耦合过重的代码。第 5 章会看到：正因为 `createTaskService` 把仓储、通知器、时钟都做成了可注入的依赖，它才既能用内存替身做毫秒级单测，又能接真实数据库做集成测试。
- **活文档**：`test("member 不能改别人的任务")` 比任何注释都更精确地记录了权限规则——而且它不会过期，过期就变红。

## 1.2 三种测试层级：各自证明什么，各自花多少钱

路线图要求你能说清 unit / component / integration「各自要证明的行为与成本」。用 TaskDesk Lite 的真实文件来对照：

| 层级                        | 对象举例                                                                  | 证明什么                                                     | 依赖                               | 速度/成本         |
| --------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------- | ----------------- |
| **unit（单元测试）**        | `src/domain/task-flow.ts` 状态机、`src/services/task-service.ts` 业务规则 | 单个函数/类的逻辑正确：边界值、错误路径、副作用              | 无外部依赖（用替身）               | 毫秒级，最便宜    |
| **component（组件测试）**   | `src/ui/task-form.tsx` 表单                                               | 用户视角的交互正确：必填错误、提交、disabled、服务器错误展示 | jsdom 模拟 DOM                     | 几十毫秒~百毫秒级 |
| **integration（集成测试）** | `src/api/app.ts` + inject、`src/db/task-repository.ts` + PGlite           | 多个真实部件拼起来仍然正确：HTTP 边界、SQL 语义、事务        | 真实框架实例、真实（嵌入式）数据库 | 百毫秒~秒级，最贵 |

三个关键认知：

**1. 每层只能证明自己的事，不能互相替代。**
单元测试把数据库 mock 掉了，那它就永远无法证明「唯一约束真的会拦截重复标题」——那是第 9 章集成测试的工作。反过来，集成测试跑一次要建库、迁移、走完整调用链，用它来穷举状态机的 4×4 迁移矩阵就是浪费：单元测试 3 毫秒就能穷举完。

**2. 层级越高，越接近用户，也越慢、越脆。**
经典的「测试金字塔」建议：大量快速的单元测试打底，适量组件/集成测试验证拼装，少量端到端测试（阶段 13 的 Playwright）验证关键用户旅程。金字塔不是教条，但它背后的成本逻辑是硬约束：如果 90% 的测试都是重量级集成测试，每次改动要等五分钟，团队就会开始跳过测试。

**3. 「测什么」由风险决定，不由代码行数决定。**
`permissions.ts` 只有 30 行，但它是越权漏洞的最后一道防线，值得穷举测试；`console-notifier.ts` 只是打日志，一行不测也没有风险。第 10 章讲覆盖率时会回到这一点：覆盖率只是「哪些代码没被执行过」的信号，而测试的价值取决于**你断言的行为有多重要**。

### TaskDesk Lite 的分层落点

后面章节会严格按照这张表组织测试（配套工程的三个 Vitest projects 就是这么划分的，见第 3 章）：

```text
test/
├── unit/           # domain 纯函数 + service（内存替身）    → 第 4、5 章
├── component/      # React Testing Library + jsdom          → 第 6、7 章
└── integration/    # Fastify inject + PGlite 真实 SQL       → 第 8、9 章
```

## 1.3 为什么是 Vitest

Vitest 是基于 Vite 的测试框架。对已经使用 Vite 的项目（本仓库的 React 教程全部如此），它的优势是决定性的：

- **共享同一套配置与转换管线**：你的 `resolve.alias`、JSX/TSX 转换、环境变量（`import.meta.env`）在测试里直接生效，不需要再配一遍 Babel/ts-jest。配套工程里 `@/` 别名在 dev、build、test 三处行为完全一致，就是这个机制。
- **Jest 兼容的 API**：`describe` / `it` / `expect` / `vi.fn()`（对应 Jest 的 `jest.fn()`），迁移成本极低。官方明确提供 Jest 兼容的断言与 mock API。
- **watch 模式像 HMR 一样快**：改一个源文件，Vitest 沿着模块依赖图只重跑受影响的测试。
- **原生 ESM 与 TypeScript**：`import`/`export`、顶层 `await`、`.tsx` 开箱即用。第 9 章的数据库测试就依赖顶层 `await` 建库。
- **一套工具覆盖全栈**：同一个 `vitest` 命令跑 Node 环境的 API 测试和 jsdom 环境的组件测试（靠 `environment` 配置切换，见第 3 章），不需要前端一个测试框架、后端另一个。

与 Jest 的主要差异（迁移时会碰到）：配置文件是 `vitest.config.ts`；mock 工具挂在 `vi` 而不是 `jest` 上；默认 ESM，`vi.mock` 会被提升到文件顶部执行（第 5 章详述）；Vitest 5 起 `clearMocks` 默认为 `true`（每个测试前自动清空 mock 调用记录，Jest 默认不清）。

## 1.4 路线预览：这个教程最终要做到什么

对照路线图阶段 12 的通过标准，学完全部章节后你的 TaskDesk Lite 应该达到：

1. **测试不依赖执行顺序、不因共享 Query cache/store 而互相污染** —— `npm run test:shuffle` 乱序执行仍然全绿（第 7、11 章）。
2. **重要错误分支和权限规则有明确断言，而非只测默认成功路径** —— 越权 403、非法迁移 422、重名 409、校验 400，每条错误路径都有测试钉住（第 4、8 章）。
3. **能用测试快速定位回归，避免过度 mock 造成「所有测试通过但系统无法运行」** —— service 单测用替身、集成测试保留真实数据库与真实 Fastify，两层互补（第 5、9 章）。

还有一个隐性目标：**测试要快**。配套工程 105 个测试全量跑完约 2~3 秒。测试慢是团队放弃测试的头号原因，所以「能低层测的不上高层、能并行的不串行」会贯穿全书。

## 1.5 常见疑问

**Q：先写代码还是先写测试（TDD）？**
本教程采用「先有代码、再补测试」的顺序，因为学习期你需要先看清被测对象。但实际工作中更高效的节奏是小步 TDD：写一个失败的测试 → 写最少代码让它通过 → 重构。第 11 章的日常工作流会给出建议循环。无论哪种顺序，**测试必须能在没有原作者的情况下独立读懂**——这是第 4 章命名规范的主题。

**Q：所有代码都要测吗？**
不。入口文件（`server.ts`、`main.tsx`）只做组装，没有分支逻辑，配套工程把它们排除在覆盖率之外（第 10 章）。测试预算优先花在：业务规则、权限、数据边界、错误处理——即「出错代价高」的地方。

**Q：Vitest 5 的 Browser Mode 是什么，本教程用吗？**
Vitest 官方现在推荐用 Browser Mode（在真实浏览器里跑组件测试）做最精确的组件验证。但它需要 Playwright/WebdriverIO 驱动，环境成本高。本教程使用更普及的 jsdom + React Testing Library 路线（也是路线图阶段 12 明确要求的技能），并在第 6 章说明两者的取舍；学完阶段 13 的 Playwright 后，你可以随时升级到 Browser Mode。

## 练习

1. 打开配套工程 [example/src/domain/permissions.ts](./example/src/domain/permissions.ts)，不看测试文件，先写下你认为 `canUpdateTask` 的完整承诺清单（提示：考虑角色 × 归属的组合有几种）。然后对照 [test/unit/permissions.test.ts](./example/test/unit/permissions.test.ts)，检查自己漏了哪些组合——特别是「member 是被指派人但不是创建者」这种情况。
2. 用你自己的话回答：为什么「任务状态机迁移矩阵」适合单元测试，而「重复标题必须被数据库唯一约束拦截」必须用集成测试？（答案要点：前者是纯逻辑、无依赖；后者依赖真实数据库的约束行为，mock 出来的假约束只能证明你的 mock 写对了。）
