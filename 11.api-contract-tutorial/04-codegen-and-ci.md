# 第 4 章：从 OpenAPI 生成客户端，并让 CI 守住它

> 本章目标：从 `openapi.json` 生成前端类型与请求封装，让前端代码**不再手写任何 API 类型**；再写一个漂移检查脚本，让 CI 在「改了接口却没重新生成」时失败。最后亲眼看看：契约一变，编译器会在哪里报错。
>
> 对应核心概念：**② 从 OpenAPI 生成客户端类型或请求封装，保持 apps/web 不直接依赖服务端实现文件。**
> 对应动手练习：**练习 1：生成或更新 OpenAPI 后运行客户端类型生成脚本，并让 CI 检查生成结果是否过期。**

---

## 4.1 生成什么？两条路线

「从 OpenAPI 生成客户端」有两种风格：

|            | 生成完整 SDK                                                          | 只生成类型 + 通用请求库                         |
| ---------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| 代表工具   | orval、@hey-api/openapi-ts、openapi-generator                         | **openapi-typescript + openapi-fetch**          |
| 生成物     | 每个接口一个函数（`createTask()`），有时连 React Query hooks 都生成好 | 一个只有类型的 `.ts` 文件                       |
| 运行时体积 | 随接口数量增长                                                        | 固定（openapi-fetch 约 6 KB），类型在编译后消失 |
| 灵活性     | 受生成器模板约束                                                      | 你自己决定怎么封装、怎么接 TanStack Query       |
| 学习价值   | 黑盒                                                                  | 每一层都看得见                                  |

两条路线都能达到「前端不手写类型」的目标。本教程选择第二种：**生成物只有类型**，所有运行时行为（CSRF 头、requestId、错误规整）都是我们自己写的、看得见的代码。理解了这一套，再去用 orval 之类的工具，你会清楚它替你做了什么。

## 4.2 生成类型：openapi-typescript

`packages/api-client/package.json` 里已经有：

```json
"generate": "openapi-typescript openapi.json --output src/generated/openapi.ts"
```

运行：

```bash
pnpm --filter @taskflow/api-client generate
# ✨ openapi-typescript 7.13.0
# 🚀 openapi.json → src/generated/openapi.ts [39.6ms]
```

生成的文件有三个主要导出（节选）：

```ts
/**
 * This file was auto-generated by openapi-typescript.
 * Do not make direct changes to the file.
 */

export interface paths {
  "/api/v1/projects/{projectId}/tasks": {
    get: operations["listTasks"];
    post: operations["createTask"];
    // ……
  };
  // ……
}

export interface components {
  schemas: {
    TaskStatus: "todo" | "doing" | "done";
    Task: {
      /** Format: uuid */
      id: string;
      title: string;
      description: string | null;
      status: components["schemas"]["TaskStatus"];
      dueDate: string | null;
      /** @description 乐观并发版本号，更新时通过 If-Match 带回 */
      version: number;
      /**
       * Format: date-time
       * @description UTC 时间点，ISO 8601 格式，带 Z 后缀
       * @example 2026-10-22T08:30:00.000Z
       */
      createdAt: string;
      // ……
    };
    CreateTaskBody: {
      title: string;
      description?: string | null;
      priority?: components["schemas"]["TaskPriority"];
      dueDate?: string | null;
    };
    // ……
  };
}

export interface operations {
  createTask: {
    parameters: {
      header: {
        /** @description 同一次「创建意图」的唯一键；网络重试时必须复用同一个值 */
        "idempotency-key": string;
      };
      path: { projectId: string };
    };
    requestBody: {
      content: { "application/json": components["schemas"]["CreateTaskBody"] };
    };
    responses: {
      /** @description 已创建（或幂等重放） */
      201: { content: { "application/json": components["schemas"]["Task"] } };
      /** @description 请求格式或字段校验失败 */
      400: {
        content: { "application/json": components["schemas"]["ErrorResponse"] };
      };
      // ……
    };
  };
}
```

注意几件事：

- 第 3 章写的 `description`、`format`、`examples` 全部变成了 JSDoc 注释，鼠标悬停就能看到；
- `Task` 是一个**有名字的类型**，这得益于第 3 章的 `$id` + `ref()`；
- 每个状态码的响应体都有类型，包括所有错误响应；
- 文件头写着「Do not make direct changes」。手改它没有意义，下次生成就会被覆盖，漂移检查也会失败。

### 生成物要不要提交？

本教程**提交**生成物（`openapi.json` 和 `src/generated/openapi.ts`）。理由：

- **评审可见**：一个 PR 改了接口，审查者能直接在 diff 里看到契约变化了什么；
- **前端不依赖后端工具链**：只改前端的同学不需要能跑起服务端才能编译；
- **漂移可检测**：提交的版本就是「已知正确」的基准，CI 重新生成后比较即可。

另一种做法是不提交、每次构建时生成。那样就不存在「过期」的问题，但会失去评审可见性，并让前端构建依赖服务端代码能运行。两种都可以，关键是**团队要选一种并自动化执行**。

## 4.3 类型安全的请求：openapi-fetch

有了类型，还需要一个能「读懂」这些类型的请求函数。`openapi-fetch` 就是一个围绕 `paths` 类型设计的 `fetch` 薄封装：

```ts
import createClient from "openapi-fetch";
import type { paths } from "./generated/openapi";

const client = createClient<paths>({ baseUrl: "" });

const { data, error, response } = await client.POST(
  "/api/v1/projects/{projectId}/tasks",
  {
    params: {
      path: { projectId },
      header: { "idempotency-key": crypto.randomUUID() },
    },
    body: { title: "写发布说明", priority: "high" },
  },
);
// data:  Task | undefined（2xx 时有值）
// error: ErrorResponse | undefined（4xx/5xx 时有值）
```

URL 是一个**字面量类型**：只能填 `paths` 里存在的路径；路径定了，`params` 和 `body` 的类型就全部确定了。

我们来实际验证它能拦住哪些错误。下面这些写法在编写本教程时都实际跑过 `tsc`，错误信息是真实输出：

```ts
// ① body 字段类型错误
api.POST("/api/v1/projects/{projectId}/tasks", { params: {...}, body: { title: 1 } });
// error TS2322: Type 'number' is not assignable to type 'string'.

// ② 漏了必填的请求头
api.POST("/api/v1/projects/{projectId}/tasks", { params: { path: { projectId: "x" } }, body: { title: "a" } });
// error TS2741: Property 'header' is missing in type '{ path: { projectId: string; }; }' but required ...

// ③ 查询参数类型错误
api.GET("/api/v1/projects/{projectId}/tasks", { params: { path: {...}, query: { limit: "10" } } });
// error TS2322: Type 'string' is not assignable to type 'number'.

// ④ 路径不存在
api.GET("/api/v1/projectz");
// error TS2554: Expected 2 arguments, but got 1.（错误信息不直观，但确实报错了）

// ⑤ 返回值的类型
const data = await unwrap(api.GET("/api/v1/projects"));
const n: number = data.items;
// error TS2322: Type '{ id: string; name: string; myRole: "owner" | "editor" | "viewer"; createdAt: string; }[]' is not assignable to type 'number'.
```

### 一个需要知道的盲区：内联 body 的多余字段

```ts
api.POST("/api/v1/projects/{projectId}/tasks", {
  params: {...},
  body: { title: "a", status: "done" },   // ⚠️ 不报错！
});
```

`status` 不在 `CreateTaskBody` 里，但这里**没有**报错。原因是 openapi-fetch 的方法用泛型推导参数类型，而 TypeScript 的「多余属性检查」只对**直接赋值给已知类型**的对象字面量生效，对泛型推导出的类型不生效。

应对方法：先把请求体赋给一个**显式标注类型**的变量或函数返回值：

```ts
const body: CreateTaskBody = { title: "a", status: "done" };
// error TS2353: Object literal may only specify known properties, and 'status' does not exist in type ...
```

这正是第 5 章 `toCreateTaskBody(values): CreateTaskBody` 存在的原因之一。当然，就算前端漏掉了，服务端的 `additionalProperties: false` 也会返回 400——两层防线。

## 4.4 我们自己的封装：`createApiClient` 与 `unwrap`

openapi-fetch 提供了中间件机制，我们用它实现所有「每个请求都要做」的事。

**`packages/api-client/src/client.ts`**：

```ts
import createClient, { type Middleware } from "openapi-fetch";
import { NetworkError, isAbortError, toApiError } from "./errors";
import type { paths } from "./generated/openapi";

const UNSAFE_METHODS = new Set(["POST", "PUT", "PATCH", "DELETE"]);

export interface ApiClientOptions {
  /** 同源部署（Vite 代理 / 反向代理）留空；跨源部署填 API 源，例如 https://api.example.com */
  baseUrl?: string;
  /** 读取当前会话的 CSRF token（来自 GET /api/v1/auth/session） */
  getCsrfToken: () => string | null;
  /** 测试时注入假的 fetch */
  fetch?: (input: Request) => Promise<Response>;
}

/**
 * 唯一的 HTTP 出口。类型全部来自 openapi.json 生成的 paths，
 * apps/web 不需要、也不允许 import 服务端源码。
 */
export function createApiClient(options: ApiClientOptions) {
  const client = createClient<paths>({
    baseUrl: options.baseUrl ?? "",
    // 同源时浏览器默认就会带 Cookie；跨源部署必须 include，且服务端要配 CORS credentials
    credentials: "include",
    ...(options.fetch ? { fetch: options.fetch } : {}),
  });

  const middleware: Middleware = {
    onRequest({ request }) {
      // 前端生成的 requestId：即使请求没拿到响应，也能把前端日志和网关日志串起来
      request.headers.set("x-request-id", `web-${crypto.randomUUID()}`);
      if (UNSAFE_METHODS.has(request.method)) {
        const token = options.getCsrfToken();
        if (token) request.headers.set("x-csrf-token", token);
      }
      return request;
    },
    onError({ error }) {
      // 主动取消（AbortController / TanStack Query 取消）原样抛出，不当作网络故障
      if (isAbortError(error)) return;
      return new NetworkError("网络连接失败，请检查网络后重试", {
        cause: error,
      });
    },
  };
  client.use(middleware);
  return client;
}

export type ApiClient = ReturnType<typeof createApiClient>;

/**
 * 把 openapi-fetch 的 { data, error, response } 变成「成功返回 data，失败抛 ApiError」，
 * 正好符合 TanStack Query 的 queryFn / mutationFn 约定。
 */
export async function unwrap<T>(
  pending: Promise<{ data?: T; error?: unknown; response: Response }>,
): Promise<T> {
  const { data, error, response } = await pending;
  if (!response.ok) throw toApiError(error, response);
  return data as T;
}
```

为什么要 `unwrap`？openapi-fetch 不会在 4xx/5xx 时抛异常，而是返回 `{ error }`。但 TanStack Query 判断「失败」的依据是 `queryFn` **抛出异常**——如果直接返回 `{ data: undefined, error }`，Query 会认为请求成功了，数据是 `undefined`。`unwrap` 把两种风格接上，并在抛出前把错误规整成统一的 `ApiError`（第 6 章）。

`unwrap` 的泛型 `T` 由传入的 Promise 推导，所以 `await unwrap(api.GET("/api/v1/projects"))` 的类型就是 `ProjectList`，不需要任何手写标注。

**`packages/api-client/src/index.ts`**（对外导出）：

```ts
import type { components, operations, paths } from "./generated/openapi";

export {
  createApiClient,
  unwrap,
  type ApiClient,
  type ApiClientOptions,
} from "./client";
export {
  ApiError,
  NetworkError,
  isAbortError,
  parseRetryAfter,
  toApiError,
  type ErrorCode,
  type FieldError,
} from "./errors";

export type { components, operations, paths };

// 常用 schema 的别名：前端只从这里拿类型，不手写第二份
type Schemas = components["schemas"];
export type Task = Schemas["Task"];
export type TaskPage = Schemas["TaskPage"];
export type TaskStatus = Schemas["TaskStatus"];
export type TaskPriority = Schemas["TaskPriority"];
export type CreateTaskBody = Schemas["CreateTaskBody"];
export type UpdateTaskBody = Schemas["UpdateTaskBody"];
export type Project = Schemas["Project"];
export type Session = Schemas["Session"];
export type User = Schemas["User"];
```

这些别名是**引用**，不是复制。`Task` 永远等于生成文件里的 `components["schemas"]["Task"]`，契约一变它就跟着变。这就是「前端代码不复制维护第二套 API 响应类型」的具体做法。

前端代码里应该只看到这样的导入：

```ts
import { unwrap, type Task, type CreateTaskBody } from "@taskflow/api-client";
```

## 4.6 漂移检查：让 CI 发现「忘了生成」

人总会忘。有人改了 `contract/tasks.ts`，测试也都过了，就是忘了跑 `contract:generate`。结果仓库里的 `openapi.json` 和前端类型还是旧的——前端编译通过，上线后才出问题。

漂移检查的思路很简单：**在 CI 里从当前代码重新生成一遍，和仓库里提交的版本逐字节比较。**

**`scripts/check-contract.mjs`**：

```js
/**
 * 契约漂移检查：
 * 1. 从当前服务端代码重新导出 OpenAPI 到临时目录；
 * 2. 用临时 OpenAPI 重新生成客户端类型；
 * 3. 与仓库里提交的 openapi.json / generated/openapi.ts 逐字节比较。
 * 任何不一致都说明「有人改了接口却没重新生成」，CI 直接失败。
 */
import { execFileSync } from "node:child_process";
import { mkdirSync, readFileSync, rmSync } from "node:fs";
import { resolve } from "node:path";

const root = resolve(import.meta.dirname, "..");
const tmp = resolve(root, ".contract-tmp");
rmSync(tmp, { recursive: true, force: true });
mkdirSync(tmp, { recursive: true });

const run = (args) =>
  execFileSync("pnpm", args, { cwd: root, stdio: "inherit" });

run([
  "--filter",
  "@taskflow/api",
  "exec",
  "tsx",
  "src/scripts/export-openapi.ts",
  `${tmp}/openapi.json`,
]);
run([
  "--filter",
  "@taskflow/api-client",
  "exec",
  "openapi-typescript",
  `${tmp}/openapi.json`,
  "--output",
  `${tmp}/openapi.ts`,
]);

const pairs = [
  ["packages/api-client/openapi.json", `${tmp}/openapi.json`],
  ["packages/api-client/src/generated/openapi.ts", `${tmp}/openapi.ts`],
];

let stale = false;
for (const [committed, fresh] of pairs) {
  let before = "";
  try {
    before = readFileSync(resolve(root, committed), "utf8");
  } catch {
    // 文件不存在也算过期
  }
  if (before !== readFileSync(fresh, "utf8")) {
    console.error(`✗ ${committed} 已过期`);
    stale = true;
  } else {
    console.log(`✓ ${committed} 与服务端代码一致`);
  }
}
rmSync(tmp, { recursive: true, force: true });

if (stale) {
  console.error(
    "\n契约产物与代码不一致：请运行 pnpm contract:generate 并提交生成结果。",
  );
  process.exit(1);
}
```

（记得把 `.contract-tmp/` 加进 `.gitignore`。）

为什么不直接用 `git diff --exit-code`？那也是常见做法：

```bash
pnpm contract:generate
git diff --exit-code -- packages/api-client
```

它的局限是：只能在 git 仓库里用；`git diff` 默认看不到**新增的未跟踪文件**（第一次生成时文件根本不存在）；并且会直接改写工作区。上面的脚本生成到临时目录，不碰工作区，在任何环境都能跑，也覆盖了「文件不存在」的情况。两种方式选一种即可。

### 亲手制造一次漂移

我们给任务状态加一个 `blocked`，但**故意不重新生成**：

```bash
# 修改 apps/api/src/contract/tasks.ts：
#   Type.Enum(["todo", "doing", "done"], ...) → Type.Enum(["todo", "doing", "blocked", "done"], ...)

pnpm contract:check
# ✗ packages/api-client/src/generated/openapi.ts 已过期
#
# 契约产物与代码不一致：请运行 pnpm contract:generate 并提交生成结果。
# [ELIFECYCLE] Command failed with exit code 1.
```

检查失败，退出码为 1，CI 会变红。把修改撤销后再运行：

```bash
pnpm contract:check
# ✓ packages/api-client/openapi.json 与服务端代码一致
# ✓ packages/api-client/src/generated/openapi.ts 与服务端代码一致
```

## 4.7 契约变更在编译期暴露

漂移检查回答的是「生成物是不是最新的」。另一个更重要的问题是：**契约变了以后，前后端哪些代码需要跟着改？**

我们做一个真实实验：给优先级增加一个 `urgent`，然后正常地运行 `contract:generate`，再分别对前后端做类型检查。

```bash
# apps/api/src/contract/tasks.ts：
#   Type.Enum(["low", "medium", "high"]) → Type.Enum(["low", "medium", "high", "urgent"])
pnpm contract:generate
pnpm typecheck
```

**前端报错**（真实输出）：

```
src/features/tasks/TaskList.tsx(65,30): error TS2741: Property 'urgent' is missing in type
  '{ readonly low: "低"; readonly medium: "中"; readonly high: "高"; }'
  but required in type 'Record<"high" | "low" | "medium" | "urgent", string>'.
src/features/tasks/task-form-schema.ts(16,12): error TS2741: Property 'urgent' is missing in type
  '{ readonly low: "低"; readonly medium: "中"; readonly high: "高"; }'
  but required in type 'Record<"high" | "low" | "medium" | "urgent", string>'.
```

前端的「优先级 → 中文标签」映射表用了 `satisfies Record<TaskPriority, string>`（第 5 章），新增的枚举值没有标签，编译器立刻指出。

**服务端也报错了**：

```
src/services/task-service.ts(260,12): error TS2345: ...
  Types of property 'priority' are incompatible.
    Type '"urgent"' is not assignable to type '"high" | "low" | "medium" | ...'.
```

API 契约允许 `urgent`，但数据库的 `pgEnum("task_priority", ["low", "medium", "high"])` 不允许。Drizzle 的类型让这个不一致在编译期暴露——你需要同时写一个数据库迁移。

这就是「契约变更会在编译或 CI 中暴露」的完整含义：

```
改契约 ──► contract:generate ──► 前端类型变了 ──► tsc 指出所有受影响的前端代码
   │
   └─────────────────────────► 服务端类型变了 ──► tsc 指出不一致的数据库/业务代码

忘了 generate ──► contract:check 失败
```

实验做完，把 `urgent` 去掉并重新生成。

## 4.8 CI 流水线

**`.github/workflows/ci.yml`**：

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]

jobs:
  contract-and-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile

      # ① 生成物是否过期：改了路由 schema 却没重新生成 → 失败
      - name: Contract drift check
        run: pnpm contract:check

      # apps/web 不允许绕过 api-client 直接引用服务端代码
      - name: Dependency boundaries
        run: pnpm boundaries:check

      # ② 契约本身是否是合法的 OpenAPI
      - name: Lint OpenAPI
        run: pnpm --filter @taskflow/api-client lint:openapi

      # ③ 前后端各自编译：契约变化导致的类型错误在这里暴露
      - run: pnpm typecheck

      # ④ 契约测试、错误映射测试、组件测试
      - run: pnpm test

  breaking-changes:
    # 只在 PR 上比较「main 的契约」与「本分支的契约」
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - name: Extract base contract
        # 写在工作区内：oasdiff 是 Docker Action，只能看到挂载进容器的工作区文件
        run: git show origin/${{ github.base_ref }}:packages/api-client/openapi.json > base-openapi.json
      - name: Detect breaking changes
        uses: oasdiff/oasdiff-action/breaking@main
        with:
          base: base-openapi.json
          revision: packages/api-client/openapi.json
          fail-on: ERR
          review: false # 不把契约上传到第三方
```

五道检查各管一件事：

| 检查               | 回答的问题                   | 失败时说明                               |
| ------------------ | ---------------------------- | ---------------------------------------- |
| `contract:check`   | 生成物和代码一致吗？         | 有人改了接口没生成                       |
| `boundaries:check` | 前端有没有绕过契约？         | 有人 import 了服务端代码                 |
| `lint:openapi`     | 契约是合法的 OpenAPI 吗？    | schema 写错了、引用断了                  |
| `typecheck`        | 前后端代码和契约一致吗？     | 契约变了，调用方没跟上                   |
| `breaking-changes` | 这次改动会不会弄坏老客户端？ | 删字段、改类型、加必填参数……（第 12 章） |

`lint:openapi` 用的是 Redocly CLI。在本项目上它的输出是：

```
validating openapi.json...
openapi.json:
  3:3  warning  info-license  Info object should contain `license` field.

Woohoo! Your API description is valid. 🎉
You have 1 warning.
```

只有一个关于 license 的警告（内部 API 可以忽略，或在 `info` 里补上 `license`）。

## 4.9 给 api-client 写测试

`packages/api-client` 是所有请求的必经之路，值得单独测试。用注入的假 `fetch`，不需要启动服务器（**`packages/api-client/test/client.test.ts`** 节选）：

```ts
function clientWith(handler: (req: Request) => Promise<Response> | Response) {
  const seen: Request[] = [];
  const api = createApiClient({
    baseUrl: "http://api.test",
    getCsrfToken: () => "csrf-123",
    fetch: async (req) => {
      seen.push(req);
      return handler(req);
    },
  });
  return { api, seen };
}

it("写请求带 CSRF 头，读请求不带；每个请求都带 requestId", async () => {
  const { api, seen } = clientWith(() =>
    json(200, { items: [], nextCursor: null }),
  );
  await api.GET("/api/v1/projects/{projectId}/tasks", {
    params: { path: { projectId: PROJECT } },
  });
  await api.POST("/api/v1/projects/{projectId}/tasks", {
    params: {
      path: { projectId: PROJECT },
      header: { "idempotency-key": crypto.randomUUID() },
    },
    body: { title: "x" },
  });
  expect(seen[0]?.headers.get("x-csrf-token")).toBeNull();
  expect(seen[1]?.headers.get("x-csrf-token")).toBe("csrf-123");
  expect(seen[0]?.headers.get("x-request-id")).toMatch(/^web-/);
});

it("fetch 本身失败 → NetworkError；主动取消 → 原样的 AbortError", async () => {
  const offline = clientWith(() => {
    throw new TypeError("Failed to fetch");
  });
  await expect(offline.api.GET("/api/v1/projects")).rejects.toBeInstanceOf(
    NetworkError,
  );
  // ……
});
```

注意测试里调用 `api.GET(...)` 时，路径和参数**同样受类型检查**——测试代码也不可能和契约漂移。

## 4.10 常见坑

| 现象                                           | 原因                                     | 解决                                |
| ---------------------------------------------- | ---------------------------------------- | ----------------------------------- |
| 生成的类型叫 `def-0`、`def-1`                  | 没配置 `refResolver.buildLocalReference` | 第 3.6 节                           |
| 生成的是匿名内联结构，没有 `Task` 类型         | 路由里内联了 schema，而不是 `ref()`      | 共享 schema 用 `$id` + `ref()`      |
| 漂移检查在 CI 总是失败，本地却通过             | 导出结果依赖环境变量 / 依赖版本不同      | 导出用固定配置；`--frozen-lockfile` |
| 4xx 时 `useQuery` 显示成功、数据为 `undefined` | openapi-fetch 不抛异常                   | 用 `unwrap()` 包一层                |
| 内联 `body` 多写了字段却不报错                 | 泛型推导不触发多余属性检查               | 先赋给显式类型的变量                |
| `openapi-typescript` 安装失败                  | 与 TypeScript 7 的 peer 冲突             | 第 2.6 节：隔离 TS 5.9              |
| 手改了 `generated/openapi.ts`                  | —                                        | 永远不要手改；改源头再生成          |
