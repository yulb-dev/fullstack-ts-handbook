# 第 1 章：为什么需要 API 契约

> 本章目标：在写任何代码之前，先建立正确的心智模型——「契约」到底是什么、类型漂移是怎么发生的、有哪几种让前后端对齐的方案、本教程为什么选择「Fastify route schema → OpenAPI → 生成客户端」这条路。
>
> 对应总目标：**将前端和后端通过稳定可验证的契约连接起来，减少手写类型漂移。**

---

## 1.1 一次真实的「类型漂移」事故

先看一段非常常见的代码。前端同学根据接口文档（或者看了一眼后端返回的 JSON）手写了类型：

```ts
// apps/web/src/types.ts —— 前端手写
export interface Task {
  id: number;
  title: string;
  done: boolean;
  dueAt?: string;
}
```

后端同学也有自己的类型：

```ts
// apps/api/src/types.ts —— 后端手写
export interface Task {
  id: number;
  title: string;
  done: boolean;
  dueAt: string | null;
}
```

上线三个月后，产品要求任务支持「进行中」状态。后端做了这些修改：

1. 把 `done: boolean` 改成 `status: "todo" | "doing" | "done"`；
2. 把 ID 改成 UUID 字符串，防止别人遍历 `/tasks/1`、`/tasks/2`；
3. 把 `dueAt`（时间点）改成 `dueDate`（日历日期），因为「截止到 10 月 30 日」本来就不是一个时间点。

后端测试全部通过，部署上线。然后：

- 前端的 `task.done` 永远是 `undefined`，所有任务都显示「未完成」；
- `task.id` 是字符串了，前端某处 `id === Number(params.id)` 永远为 `false`，详情页全部 404；
- 截止日期一列全空。

**TypeScript 一个错都没报。** 因为前端的 `Task` 类型是手写的，它只是一份「我以为接口长这样」的声明，和真实接口之间没有任何机械联系。这就是**类型漂移（type drift）**：两份本应相同的类型描述，随着时间各自演化，最终不一致，而且没有任何工具能发现。

漂移的根本原因只有一个：**同一个事实被维护了两份（甚至更多份）**——后端类型、前端类型、接口文档、Postman 集合、测试 mock……每多一份，就多一个出错的机会。

---

## 1.2 什么是 API 契约

**API 契约（API contract）**是前后端之间关于「HTTP 接口长什么样」的**机器可读**的约定。一份完整的契约至少回答这些问题：

| 问题                 | 例子                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| 有哪些接口？         | `POST /api/v1/projects/{projectId}/tasks`                                                        |
| 请求要带什么？       | path 参数 `projectId`（UUID）、请求头 `Idempotency-Key`、请求体 `{ title, priority?, dueDate? }` |
| 每个字段的约束？     | `title` 1~120 个字符；`priority` 只能是 `low/medium/high`                                        |
| 可能返回哪些状态码？ | `201`、`400`、`401`、`403`、`404`、`409`、`422`、`500`                                           |
| 每个状态码的响应体？ | `201` 返回 `Task`；所有错误返回统一的 `ErrorResponse`                                            |
| 怎么认证？           | 会话 Cookie `sid`；写请求还要带 `X-CSRF-Token`                                                   |
| 列表怎么分页？       | `?limit=&cursor=`，返回 `{ items, nextCursor }`                                                  |

注意关键词「**机器可读**」。一篇写在 Wiki 上的接口文档也是一种约定，但它不能被编译器检查、不能被测试验证、不能自动生成代码——它和手写类型一样会漂移。

本教程用 **OpenAPI 3.1** 作为契约的格式。OpenAPI 是描述 HTTP API 的行业标准，本质上就是一个 JSON（或 YAML）文件，它的数据模型部分直接使用 **JSON Schema**。有了它：

- 可以生成交互式文档（本项目用 Scalar，在 `/docs` 查看）；
- 可以生成前端 TypeScript 类型和请求封装；
- 可以在 CI 里比较两个版本，自动发现破坏性变更；
- 可以在测试里用它校验真实响应。

## 1.3 让前后端对齐的四种方案

「前后端类型一致」不是新问题，业界有几种主流做法。理解它们的取舍，你才知道本教程的选择不是唯一答案，而是一个**在特定约束下合理的**答案。

### 方案 A：两边各自手写类型

就是 1.1 节的做法。成本最低，也最容易漂移。只适合原型期或一次性项目。

### 方案 B：前端直接 import 后端的类型

在 monorepo 里，前端写：

```ts
import type { Task } from "../../api/src/db/schema"; // ❌ 不推荐
```

看起来「单一事实来源」了，但问题很大：

1. **泄露实现细节**：数据库行类型里有 `passwordHash`、内部 ID、软删除标记……前端拿到的类型和真正返回的 JSON 并不一样（比如 `createdAt` 在数据库里是 `Date`，在 JSON 里是字符串）；
2. **耦合构建**：前端的类型检查要能编译后端代码（包括 Node.js 类型、数据库驱动类型），一个后端重构就可能让前端编译失败；
3. **契约不可见**：没有一个地方能看到「接口到底长什么样」，移动端、第三方、测试都用不了；
4. **安全隐患**：一不小心 `import` 了值而不是类型，打包器会把服务端代码（甚至密钥配置）打进浏览器包。

### 方案 C：tRPC / 类似的 RPC 框架

tRPC 让前端直接推导后端 router 的类型，开发体验极好。但它本质上是方案 B 的「工程化版本」：契约就是后端的 TypeScript 类型，它**只对 TypeScript 客户端有效**，没有语言无关的契约文件，对外开放、多端（iOS/Android）、网关治理、HTTP 语义（状态码、缓存、幂等头）都不是它的强项。

如果你的项目确定只有一个 TS 前端、全栈同一个团队、永远不对外，tRPC 是很好的选择。本教程的场景假设不是这样。

### 方案 D：以 OpenAPI 为契约

OpenAPI 又分两种工作流：

|      | Design-first（契约优先）                        | Code-first（代码优先）                                         |
| ---- | ----------------------------------------------- | -------------------------------------------------------------- |
| 做法 | 先手写 `openapi.yaml`，再生成服务端骨架和客户端 | 在服务端代码里声明 schema，自动导出 OpenAPI                    |
| 优点 | 契约评审可以早于实现；适合多团队、对外 API      | 契约和实现**不可能不一致**（同一份 schema 既做校验又生成文档） |
| 缺点 | 服务端实现和 yaml 可能漂移，需要额外校验        | 契约评审要看生成物；需要框架支持                               |

**本教程选择 Code-first：以 Fastify route schema 作为权威来源。** 原因是 Fastify 的 route schema 同时承担三件事：

```
                       ┌────────────────────────────┐
                       │  Fastify route schema       │
                       │  （TypeBox 写成的 JSON Schema）│
                       └──────────────┬─────────────┘
          ┌──────────────────────────┼──────────────────────────┐
          ▼                          ▼                          ▼
  ① 运行时校验请求             ② 推导 handler 的 TS 类型      ③ 生成 OpenAPI 文档
  （Ajv：不合法直接 400）      （req.body 有类型）           （@fastify/swagger）
```

同一份 schema，既是「服务端真正执行的校验」，又是「文档里写的约定」。只要服务端在跑，文档就不可能撒谎——这正是「稳定可验证」的含义。

## 1.4 本教程的整体架构

```
┌──────────────────────── packages/api-client ────────────────────────┐
│  openapi.json（从服务端导出，提交到仓库）                              │
│  src/generated/openapi.ts（openapi-typescript 生成，提交到仓库）        │
│  src/client.ts（openapi-fetch + 中间件：CSRF、requestId、网络错误）     │
│  src/errors.ts（ApiError / NetworkError：统一错误模型）                │
└───────────────▲──────────────────────────────────┬──────────────────┘
                │ 导出 OpenAPI                       │ 只依赖这个包
┌───────────────┴───────────────┐      ┌───────────▼──────────────────┐
│ apps/api                      │      │ apps/web                      │
│  contract/*.ts  TypeBox 契约   │      │  Zod 表单 schema（体验）        │
│  routes/*.ts    route schema   │      │  TanStack Query hooks          │
│  plugins/       错误/认证/CSRF  │      │  错误 → UI 映射                 │
│  services/      授权 + 业务     │      │                                │
│  db/            Drizzle        │      │  ✗ 不能 import apps/api 任何文件 │
└───────────────┬───────────────┘      └────────────────────────────────┘
                ▼
            Postgres
```

依赖方向是这份架构的灵魂：

- `apps/api` → 生成 → `packages/api-client/openapi.json`（单向，靠脚本，不靠 import）；
- `apps/web` → 依赖 → `packages/api-client`；
- `apps/web` **永远不** import `apps/api`（第 2 章用脚本强制检查）。

前端看到的世界只有「契约」，不知道服务端用的是 Fastify 还是别的框架、数据库是 Postgres 还是别的。服务端可以随意重构内部实现，只要契约不变，前端毫无感知；一旦契约变了，生成的类型跟着变，前端编译器会立刻指出所有受影响的地方。

## 1.5 一次「创建任务」请求的完整旅程

在动手之前，先把第 9、10 章要实现的链路完整走一遍。不用记住细节，只需要知道每一站在做什么、为什么需要它。

```
[浏览器]
 ① 用户在表单输入标题、优先级、截止日期，点「创建任务」
 ② React Hook Form 收集值 → zodResolver 用 Zod 校验
      失败：字段下方立刻显示错误，不发请求（体验）
 ③ toCreateTaskBody() 把表单值整理成契约要求的请求体（"" → null）
 ④ useCreateTask() 的 mutationFn 调用生成的客户端：
      api.POST("/api/v1/projects/{projectId}/tasks", { params, body })
      中间件自动加上：X-CSRF-Token、X-Request-Id；fetch 自动带上会话 Cookie
      请求头里还有 Idempotency-Key（同一次创建意图保持不变）
        │
        │  HTTP（开发期经 Vite 代理，同源，无 CORS）
        ▼
[Fastify]
 ⑤ genReqId：采用或生成 requestId，之后所有日志都带上它
 ⑥ onRequest 钩子：读 Cookie → 查会话 → request.auth
      写请求：校验 Origin、校验 X-CSRF-Token（失败 403）
 ⑦ Ajv 按 route schema 校验 params / headers / body（失败 400 + 字段错误）
 ⑧ handler：requireAuth（未登录 401）
 ⑨ Service：assertCanWrite（不是成员 404，只读 403）
 ⑩ 事务：占用幂等键 → INSERT tasks → 保存响应
      唯一约束冲突 → 409；同键不同内容 → 422；同键同内容 → 重放
        │
        ▼
[Postgres]
 ⑪ CHECK 约束、唯一索引、外键：数据正确性的最后一道防线
        │
        ▼
[Fastify]
 ⑫ toTaskDto() 把数据库行映射成契约 DTO（Date → ISO 字符串）
 ⑬ 按 response[201] schema 序列化；setErrorHandler 把任何错误转成统一 envelope
 ⑭ onSend：响应头加 X-Request-Id
        │
        ▼
[浏览器]
 ⑮ unwrap()：2xx 返回 data；否则抛 ApiError（含 status、code、fields、requestId）
 ⑯ 成功：invalidateQueries 刷新列表，表单重置，换新的幂等键
     失败：400/409 字段错误 → setError 回填到输入框
           401 → 全局回到登录页；403/404/500 → 横幅（500 显示请求编号）
```

你会发现，「把数据存进数据库」只是第 ⑩、⑪ 步，其余十几步都在回答同一个问题：**怎样让前后端对「这次请求是什么、结果是什么、出了错怎么办」达成一致，而且这种一致是可以被机器验证的。**

## 1.6 三条贯穿全书的铁律

**铁律 1：契约只有一个权威来源。**
在本项目里，它是 `apps/api` 中的 TypeBox schema。`openapi.json` 和前端类型都是**生成物**，不允许手改；任何人想改接口，都必须改源头，然后重新生成。

**铁律 2：客户端校验是体验，服务端校验是边界。**
浏览器里的一切都可以被绕过：用户可以禁用 JS、改请求、直接用 `curl`。服务端必须假设每个请求都可能是恶意构造的，独立完成全部校验、授权和业务规则检查。

**铁律 3：错误也是契约的一部分。**
「成功时返回什么」大家都会写进文档，但「失败时返回什么」往往被忽略。本教程中，每个接口的每个错误状态码都在契约里声明，所有错误共用一种结构，前端可以据此写出确定的 UI 逻辑。

## 1.7 常见误区

| 误区                                    | 为什么不对                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| 「我们有 Swagger 文档，所以有契约了」   | 手写的文档和实现可能不一致。契约要么由实现生成，要么有自动校验保证实现符合它           |
| 「前端 import 后端类型最省事」          | 泄露实现细节、耦合构建、可能把服务端代码打进浏览器（1.3 方案 B）                       |
| 「TypeScript 类型对上了，接口就没问题」 | 类型只描述形状，不描述约束（长度、格式）、状态码、认证方式。还要靠运行时校验和契约测试 |
| 「生成的代码不该提交到仓库」            | 本教程选择提交：评审时能看到契约变化，CI 能检查是否过期（第 4 章会讨论另一种做法）     |
| 「前端校验做好了，后端可以少做点」      | 铁律 2。第 5 章会用绕过测试证明这一点                                                  |
