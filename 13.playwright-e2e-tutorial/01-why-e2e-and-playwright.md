# 第 1 章：为什么需要端到端测试

> 本章目标：在写任何代码之前，先建立正确的心智模型——E2E 测试在整个测试体系里处于什么位置、它证明什么、不证明什么；Playwright 由哪些部件组成；`browser / context / page / locator` 这四个核心对象各自是什么。
>
> 对应总目标：**从真实浏览器视角验证关键用户旅程，理解隔离、可靠等待与诊断产物。**

---

## 1.1 所有单元测试都通过了，用户还是打不开页面

假设你维护一个任务管理应用。它的测试体系看起来相当健康：

- 用 Vitest 测过纯函数：状态流转、权限判断、分页参数解析，全绿；
- 用 Fastify `app.inject` 测过 API：校验、错误码、鉴权，全绿；
- 用 Testing Library 测过表单组件：必填错误、提交成功、禁用态，全绿。

上线第二天，用户反馈：**登录后一片空白**。

排查发现：前端把会话 cookie 的名字从 `sid` 改成了 `sb_session`，但登录页的跳转逻辑还在读旧名字；这个 bug 不落在任何一层测试的辖区内——纯函数没错、API 没错、组件单测里 cookie 是 mock 的。它只存在于「真实浏览器 + 真实服务端 + 真实 cookie」的组合里。

这就是**集成缝隙（integration seam）**问题：每一层各自正确，不代表组装起来正确。组件测试 mock 掉了网络，API 测试没有浏览器，单元测试两者都没有。总有一类 bug 只出现在完整链路上：

| 只在真实链路上出现的问题 | 例子                                                                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 前后端契约漂移           | 后端把 `done: boolean` 改成 `status: string`，前端还在读旧字段（参见 [API 契约教程](../11.api-contract-tutorial/README.md)） |
| 浏览器行为               | cookie 的 `SameSite` 属性导致跨站请求不带会话；`HttpOnly` 让 JS 读不到 cookie                                                |
| 渲染与时序               | 数据回来之前按钮已可点击，用户连点两次创建了两条重复记录                                                                     |
| 路由与状态               | 刷新页面后前端路由丢失查询参数，列表回到未筛选状态                                                                           |
| 权限的端到端表现         | API 返回 403 了，但前端把它吞掉，界面显示空列表而不是「无权访问」                                                            |

**端到端测试（End-to-End Test，E2E）**就是为了守住这条完整链路：启动真实浏览器，加载真实页面，像用户一样点击、输入、导航，然后断言用户能看到的结果。

## 1.2 测试金字塔：E2E 该测多少

测试金字塔按「运行成本」把测试分三层：

```
        ▲  成本 / 脆弱性
       ╱ ╲
      ╱E2E╲        少量：关键用户旅程、权限边界、跨层集成
     ╱─────╲
    ╱ 集成  ╲      适量：API + 数据库、组件 + 网络层
   ╱─────────╲
  ╱   单元    ╲    大量：纯函数、业务规则、单个组件
 ╱─────────────╲
```

- **单元测试**毫秒级、定位精准，但证明范围最小；
- **集成测试**（如 `app.inject` + 测试数据库）覆盖服务层真实行为；
- **E2E 测试**一次要启动浏览器、渲染页面、走完整网络往返，单条测试通常以秒计，失败时定位成本也最高——但它是唯一能证明「用户真的能完成这件事」的层。

由此得出两条实践准则：

1. **E2E 只测关键旅程和跨层边界**。「注册 → 登录 → 创建任务 → 修改状态 → 搜索 → 登出」值得一条 E2E；「标题超过 80 字符返回 400」用 API 集成测试更合适（快 100 倍，失败信息更精准）。
2. **不要用 E2E 补偿下层测试的缺失**。如果单元/集成层是空的，E2E 套件会又慢又脆，最终没人愿意跑它。

本教程配套的 [FlowOps 开发手册](../docs/flowops/FlowOps_开发手册.md)第 8 章的测试分层表，就是这个金字塔在毕业项目里的落地：Vitest 管单元与 API 集成，Playwright 管「真实浏览器业务流程、角色差异、组织切换」。

## 1.3 Playwright 是什么，由哪些部件组成

Playwright 是微软开源的浏览器自动化与测试框架。一句话概括它和其他方案的区别：**它直接通过调试协议驱动真实浏览器（Chromium、Firefox、WebKit），并自带一个为「网页异步性」设计的测试运行器**。

安装包只有一个：`@playwright/test`。但它内部包含四个部件，理解分工能帮你以后准确查文档：

```
┌────────────────────────────────────────────────────────┐
│  你的测试代码（tests/*.spec.ts）                          │
├────────────────────────────────────────────────────────┤
│  ① Test Runner   test / expect / fixture / 并行 / 重试    │
│  ② Assertions    web-first 断言（自动重试直到超时）        │
│  ③ Locators      语义化定位（getByRole / getByLabel …）   │
├────────────────────────────────────────────────────────┤
│  ④ Playwright Library（自动化核心）                       │
│     通过 WebSocket 与浏览器进程通信                        │
├──────────────┬──────────────┬──────────────────────────┤
│  Chromium    │   Firefox    │   WebKit                 │
│  (Chrome/Edge)│             │  (Safari 内核)            │
└──────────────┴──────────────┴──────────────────────────┘
```

- **Test Runner**：`import { test, expect } from '@playwright/test'` 里的 `test`。负责发现测试文件、分配 worker 进程、执行 fixture、重试、生成报告。它不是 Jest/Vitest 的插件，而是一个独立运行器；
- **Assertions**：`expect`。除了通用的 `toEqual` 之外，提供会自动重试的 web-first 断言（第 4 章）；
- **Locators**：`page.getByRole(...)` 等。描述「怎么找元素」，自带等待与重试（第 3 章）；
- **Library**：底层自动化 API（`page.click`、`context.route`、网络拦截等）。`playwright`（不带 test）这个包只含这一层，用于写爬虫、脚本等非测试场景——本教程始终用 `@playwright/test`。

一个容易混淆的点：**Playwright Test ≠ Playwright Library**。搜索文档时，`docs/test-*` 开头的页面属于测试运行器，`docs/api/*` 属于自动化库；两者大部分时候配合使用，但概念上要分清。

### 与同类工具的关系（简史）

如果你用过或听说过 Puppeteer / Selenium / Cypress，一张表说清 Playwright 的位置：

|                 | Selenium              | Puppeteer            | Cypress                              | Playwright                                           |
| --------------- | --------------------- | -------------------- | ------------------------------------ | ---------------------------------------------------- |
| 出现时间        | 2004                  | 2017                 | 2017                                 | 2020                                                 |
| 驱动方式        | WebDriver 协议        | CDP（主要 Chromium） | 注入页面内 JS                        | 调试协议（三引擎均定制）                             |
| 浏览器          | 全部主流              | 主要 Chromium        | Chromium 系 + Firefox + WebKit(实验) | Chromium / Firefox / WebKit                          |
| 测试运行器      | 无（需配 Mocha/Jest） | 无                   | 自带                                 | 自带                                                 |
| 多标签页/多域名 | 支持但繁琐            | 支持                 | 历史上受限                           | 原生支持                                             |
| 网络拦截        | 弱                    | 支持                 | 支持                                 | 支持（`page.route`）                                 |
| 失败诊断        | 截图                  | 自己搭               | 截图/视频                            | **Trace Viewer**（DOM 快照 + 网络 + 控制台时间旅行） |

Playwright 团队的核心成员正是从 Puppeteer 项目出来的，可以把它理解为「Puppeteer 的经验 + 自带成熟测试运行器 + 三浏览器引擎」。截至本教程写作时（1.64.x），它已是新项目中 E2E 测试的主流默认选择。

## 1.4 核心对象模型：browser / context / page / locator

这是 Playwright 最重要的心智模型，后面所有章节都建立在这四个对象上。

### Browser：浏览器进程

一个真实的浏览器进程（如一个 Chromium 实例）。启动成本高（数百毫秒到数秒），因此 Playwright Test 会**让同一个 worker 里的多个测试共享一个 browser 进程**。你几乎不需要直接操作它。

### BrowserContext：等价于一个全新的浏览器配置文件

context 是 browser 内部的**隔离沙箱**：独立的 cookie、localStorage、IndexedDB、缓存、代理设置。创建一个 context 非常轻量（毫秒级），就像打开一个无痕窗口。

**每个测试默认获得一个全新的 context**——这就是 Playwright 测试隔离的基石：上一个测试登录过、改过 localStorage，对下一个测试完全不可见。第 5 章会展开。

context 还承载了「身份」：通过 `storageState` 可以把某次登录后的 cookie/localStorage 注入新 context，让测试一打开页面就是已登录状态（第 7 章）。

### Page：一个标签页

`page` 属于某个 context，对应一个标签页，是你绝大多数操作的入口：`page.goto()`、`page.getByRole()`、`page.click()`。一个 context 可以开多个 page（多个标签页共享登录态），用于测试「弹出新窗口」之类的场景。

### Locator：一个「查找元素的策略」，而不是元素本身

这是新手最容易误解的对象。**locator 不是 DOM 元素的引用，而是一份「如何找到元素」的描述**。它有两个关键性质：

1. **惰性**：创建 locator 时不查找任何东西。`page.getByRole('button', { name: '登录' })` 只是记下策略；
2. **每次动作前重新解析**：`locator.click()` 执行时才会去 DOM 里实时查找元素，找到了才点。如果页面重渲染导致元素被替换，下一次动作会自动找到新元素。

这两点让 locator 天然免疫 React/Vue 重渲染带来的「元素引用失效」问题，也是自动等待机制的载体（第 3、4 章详解）。

四者的关系：

```
Browser（进程，worker 内共享）
 └── BrowserContext（隔离沙箱，每测试一个；携带 cookie/storage）
      └── Page（标签页，可多个）
           └── Locator（查找策略，随用随建，不持有元素）
```

## 1.5 自动等待：Playwright 对「脆弱测试」的回答

E2E 测试最大的敌人是**时序**：网页是异步的，点击按钮后数据可能 50ms 回来，也可能 3s 回来。传统方案有两种，都很糟：

```js
// ❌ 方案一：固定等待。网络快时浪费时间，网络慢时照样失败
await button.click();
await sleep(3000);
expect(result.textContent).toBe("成功");

// ❌ 方案二：立即断言。元素还没渲染出来，测试间歇性失败（flaky）
await button.click();
expect(await result.isVisible()).toBe(true);
```

固定 `sleep` 制造了「本地能过、CI 上随机挂」的 flaky 测试；而 flaky 测试比没有测试更糟——它训练团队忽略红色信号。

Playwright 的答案是把等待内置进每一个动作和断言：

- **动作前自动等待（auto-waiting）**：`click()` 之前，Playwright 会等元素出现、可见、位置稳定、可接收事件、未被禁用，全部满足才真正点击；
- **断言自动重试（web-first assertions）**：`await expect(locator).toBeVisible()` 不是「看一眼」，而是「反复看，直到满足或超时（默认 5 秒）」。

所以在 Playwright 里，正确的写法天然是健壮的：

```js
// ✅ 无需任何 sleep：click 自动等按钮可点，断言自动重试到结果出现
await page.getByRole("button", { name: "提交" }).click();
await expect(page.getByText("成功")).toBeVisible();
```

这也是学习路线图验收清单里「为什么固定 sleep、任意 timeout 会制造脆弱测试」的答案：**固定等待把「等多久」这个不可知的问题硬编码成了常量，而自动等待把判断标准换成了「条件是否满足」——条件满足立即继续（快），条件一直不满足才超时（准）。**

## 1.6 贯穿项目：TaskBoard lite

和仓库里其他教程一样，本教程有一个贯穿始终的配套工程（[example](./example)）。被测应用叫 **TaskBoard lite**：一个多工作区任务看板，具备教学所需的全部要素，又小到可以通读源码。

**技术形态**（刻意为之的极简）：

- 服务端：约 350 行的 `node:http` 单文件，内存数据，重启即重置——不需要数据库、不需要 Docker、零运行时依赖；
- 前端：原生 ESM 三件套（HTML/CSS/JS），无框架无构建——语义化标记（`label`、`role`、`dialog`）恰好是定位器教学的素材；
- 认证：邮箱 + 密码登录，`HttpOnly` cookie 会话。

**功能与教学场景的映射**：

| 应用功能                                       | 支撑的教学场景                                          |
| ---------------------------------------------- | ------------------------------------------------------- |
| 登录 / 登出、会话 cookie                       | storageState 认证复用（第 7 章）、游客边界（第 7 章）   |
| 双工作区 Alpha / Beta，成员互不可见            | 跨租户越权测试（第 12 章练习 2）                        |
| 任务创建 / 改状态 / 删除 / 详情对话框          | 关键旅程（第 12 章练习 1）、表单与对话框交互（第 9 章） |
| 搜索（回车触发）/ 状态筛选 / 分页              | 列表断言、键盘交互、分页（第 3、9 章）                  |
| 内部备注仅管理员可见可改                       | 角色差异测试（第 7 章）                                 |
| 统一的 `{ error: { code, message } }` 错误模型 | 网络失败注入、错误态断言（第 8、9 章）                  |

**测试账号**（仅本地学习用）：

| 用户  | 邮箱                  | 密码       | 工作区      | 角色   |
| ----- | --------------------- | ---------- | ----------- | ------ |
| Alice | `alice@taskboard.dev` | `alice123` | Alpha       | member |
| Bob   | `bob@taskboard.dev`   | `bob123`   | Beta        | member |
| Carol | `carol@taskboard.dev` | `carol123` | Alpha、Beta | admin  |

一个值得注意的服务端约定：**非成员访问任何工作区资源一律返回 403，包括资源根本不存在的时候**。如果「不存在」回 404、「无权」回 403，攻击者就能靠响应差异枚举出哪些任务 id 真实存在。第 12 章会专门测这个行为。

## 1.7 E2E 测试的成本与边界（何时不写）

最后泼一盆冷水，避免走向另一个极端——「什么都用 E2E 测」：

- **慢**：一条 E2E 通常 2~10 秒，是单元测试的百倍。500 条 E2E 跑一轮要半小时，你会开始跳过它；
- **定位成本高**：单元测试失败直接指向函数；E2E 失败可能是前端、后端、网络、测试代码自身任何一环，需要 Trace Viewer 这样的专门工具（第 10 章）；
- **不该测的**：纯业务规则（下沉到单元层）、API 输入校验矩阵（下沉到集成层）、第三方网站的行为（你控制不了它，见官方最佳实践「Avoid testing third-party dependencies」）。

**E2E 的黄金判据：这件事失败了，用户会打电话投诉吗？**会——写 E2E；不会——往下层放。

## 常见误区

1. **「有了 Vitest 就不需要 Playwright」**：两者证明的命题不同。Vitest 证明「零件合格」，Playwright 证明「整机能开」。1.1 节的空白页事故两层都拦不住。
2. **「Playwright 只是一个浏览器驱动库」**：它的测试运行器（fixture、并行、重试、trace）才是日常收益最大的部分，别拿它配 Jest 用。
3. **「locator 就是元素的别名」**：locator 是策略不是引用，每次动作都重新查找。理解这一点才能理解它为什么不怕重渲染。
4. **「E2E 越多越好」**：E2E 在金字塔顶端，只覆盖关键旅程与跨层边界；用数量堆安全感只会得到又慢又脆的套件。

## 练习

1. 判断以下场景该放在哪一层测试（单元 / API 集成 / E2E），并说明理由：
   a. 任务标题允许 1~80 个字符，越界返回 400；
   b. 用户登录后刷新页面仍然是登录态；
   c. 非管理员修改「内部备注」字段被拒绝；
   d. Alice 无法通过任何途径看到 Beta 工作区的任务；
   e. 状态字符串 `"doing"` 到 `"done"` 的流转合法性。
2. 用你自己的话解释：为什么「每个测试一个全新的 BrowserContext」是测试隔离的基石？如果所有测试共用一个 context，会发生什么？
3. 解释 locator 的「惰性 + 每次动作重新解析」两个性质分别解决了什么问题。

<details>
<summary>参考答案</summary>

1. a—API 集成（校验矩阵，快且精准）；b—E2E（cookie + 前端路由 + 服务端会话的跨层行为）；c—两层都要：API 集成测 403 本身，E2E 测「界面上备注输入框不可见/保存报错」的用户可观察表现；d—E2E（这是权限的端到端表现，正是 12 章练习 2）；e—单元（纯函数）。
2. context 携带 cookie、localStorage 等全部浏览器状态。共用 context 意味着测试 A 的登录态、A 写入的缓存会泄漏给测试 B：B 的结果依赖 A 是否跑过、以什么顺序跑过，无法单独重跑，失败还会级联。每测试一个全新 context，则每个测试都从「刚打开浏览器」的确定状态出发。
3. 惰性：创建 locator 时元素可能还不存在（页面没加载完），立即查找必然失败；推迟到动作时才解析就没有这个问题。每次重新解析：SPA 重渲染会销毁并重建 DOM 节点，持有旧引用会点到「已死」的元素；按策略重查永远拿到当前活着的节点。

</details>
