# 第 1 章：为什么需要 Monorepo

> 本章目标：建立心智模型——搞清楚 monorepo 到底解决什么问题、又会带来什么新问题；分清 **pnpm**（把仓库「组织对」）与 **Turborepo**（把任务「跑得快、跑得准」）各自的职责，避免把它们混为一谈。
>
> 对应核心概念：**总目标——把 web、api、共享 schema/类型与测试组织到可复现、可缓存的仓库结构中。**

---

## 1.1 一个真实的场景：三个仓库的痛

假设你在做一个任务协作产品，团队按「前端 / 后端」分了两个仓库，外加一个「公共类型」仓库：

```
workboard-web/       # React 前端
workboard-api/       # Fastify 后端
workboard-shared/    # 前后端共用的类型与校验，发布到私有 npm
```

一开始很清爽。三个月后，你会陆续遇到这些事：

**场景一：一次改动的「三仓库华尔兹」。** 后端要把任务的 `dueAt` 字段改名成 `dueDate`。正确的合并顺序是：先发 `shared` 新版本 → 再让 `api` 和 `web` 各自升级 `shared` → 三者同时上线。现实是：`shared` 发了 `1.4.0`，`api` 升了，`web` 的同学还在休假没升，线上前端读 `task.dueAt` 全是 `undefined`。**一次原子改动，被拆成了三个非原子的 PR。**

**场景二：版本地狱。** `web` 用 `zod@3.22`，`api` 用 `zod@3.23`，`shared` 的 peer 写着 `zod@^3.20`。同一个 schema 在两边行为微妙不同，一个 bug 只在其中一个版本复现，你花两天定位到「原来是 zod 小版本差异」。

**场景三：本地环境不可复现。** 新人入职，README 写着：

```
1. clone workboard-shared，pnpm install，pnpm link
2. clone workboard-api，pnpm link workboard-shared，pnpm install
3. clone workboard-web，pnpm link workboard-shared，pnpm install
4. 保证三个仓库都在正确的分支上……
```

第 3 步就报错了，因为你机器上 pnpm 版本和他不一样。

这些痛点的根源是：**代码在逻辑上是紧密耦合的（它们共享契约、必须协同演进），但在物理上被拆成了独立发布单元**。仓库边界和依赖边界不匹配。

---

## 1.2 Monorepo 是什么，不是什么

**Monorepo（单一仓库 / mono-repository）** 指的是：把多个在逻辑上相关的项目，放进**同一个版本控制仓库**里管理。注意关键词：

- ✅ 它是「**一个仓库，多个包（package）**」；
- ❌ 它**不是**「把整个公司所有不相关的项目塞进一个巨型仓库」（那是 monolith，另一回事）；
- ❌ 它**不是**一个具体的工具，而是一种**仓库组织策略**。pnpm、Turborepo、Nx、Lerna、Bazel 都是实现这种策略的工具。

回到上面的场景，monorepo 如何化解：

| 多仓的痛           | Monorepo 的解法                                                             |
| ------------------ | --------------------------------------------------------------------------- |
| 三仓库华尔兹       | 一次 commit 同时改 `api` 和 `web`，一个 PR、一次 review、一次上线，**原子** |
| 版本地狱           | 全仓一个 lockfile、一份 `catalog:` 统一版本，`zod` 只有一个                 |
| 本地不可复现       | `pnpm install` 一条命令装齐全仓，`packageManager` 字段锁定包管理器版本      |
| 共享代码要「发布」 | 包之间用 `workspace:*` 直接链接，改了立刻生效，无需发版                     |
| 契约漂移           | `api` 改了 schema，同一 PR 里 `web` 的类型检查立刻失败，**编译期就发现**    |

**但 monorepo 也带来新问题**，这正是本教程后半段（Turborepo）要解决的：

1. **规模**：仓库一大，`pnpm install`、全量 build、全量 test 会越来越慢。你不希望改一行注释就重跑二十分钟 CI。
2. **任务顺序**：`web` 依赖 `api-client`，`api-client` 依赖 `api` 导出的 OpenAPI。这些任务必须按依赖顺序跑，还要尽量并行。
3. **重复劳动**：CI 每次都从零构建，即使大部分包根本没变。
4. **边界失控**：仓库里所有代码物理上都能互相 import，前端一不小心就 `import` 了服务端的数据库代码。

**结论**：monorepo 让「协同改动」变简单，但让「高效、有序、有边界地运行」变复杂。我们需要两把工具各管一头。

## 1.3 pnpm 与 Turborepo 的分工（本教程的主线）

这是最容易混淆的一点，先钉死：

```
┌─────────────────────────────────────────────────────────────┐
│  pnpm  ——「包管理器 + workspace」                            │
│  负责：依赖安装、node_modules 结构、包之间怎么链接、           │
│        lockfile、版本统一、按包过滤执行脚本                    │
│  回答：这个仓库有哪些包？它们各自依赖什么？怎么装？             │
└─────────────────────────────────────────────────────────────┘
                            ↓ 装好之后
┌─────────────────────────────────────────────────────────────┐
│  Turborepo  ——「任务编排器 + 缓存」                          │
│  负责：定义任务（build/test/lint）、任务之间的依赖顺序、        │
│        并行执行、增量缓存（只跑受影响的）、远程缓存            │
│  回答：这些包的 build/test 按什么顺序跑？哪些能跳过（缓存）？   │
└─────────────────────────────────────────────────────────────┘
```

一个类比：

- **pnpm 像「仓库管理员 + 采购」**：它知道货架上有哪些包（package），每个包需要哪些零件（dependencies），负责把零件按正确的、不冲突的方式摆好（`node_modules`），并记一本唯一的账（lockfile）。
- **Turborepo 像「车间调度 + 记忆」**：它知道要生产哪些东西（tasks），谁必须先于谁（`dependsOn`），哪些工序可以并行，以及「这个零件上次做过、输入没变，直接拿成品」（cache）。

**它们不是竞争关系，而是接力关系**。你甚至可以只用 pnpm 不用 Turborepo（小仓库），或用别的编排器。但在本系列的技术栈里，pnpm + Turborepo 是最主流的组合——路线图推荐结构里，`pnpm-workspace.yaml` 和 `turbo.json` 是并排出现在仓库根目录的。

> **一句话记忆**：**pnpm 管「依赖与包」，Turborepo 管「任务与缓存」。** 后面每一章你都可以问自己：我现在解决的问题，属于哪一边？

## 1.4 为什么不直接用 npm / yarn workspaces？

npm 和 yarn 也有 workspaces 功能，能用吗？能。但 pnpm 在 monorepo 场景有两个决定性优势，这也是本系列选它的原因：

### 优势一：严格的 `node_modules`，消灭「幽灵依赖」

npm/yarn 会把依赖「扁平化提升（hoist）」到根 `node_modules`。副作用是：即使你**没有**在 `package.json` 里声明 `lodash`，只要它是某个依赖的依赖被提升上来了，你也能 `import lodash` 且编译通过。这叫**幽灵依赖（phantom dependency）**。

它有多危险？某天那个真正依赖 `lodash` 的包升级后不再依赖它，`lodash` 从根 `node_modules` 消失，你的代码**突然就崩了**——而你从没声明过它，排查时一脸茫然。

pnpm 用「符号链接 + 内容寻址存储」的结构，让**每个包只能 import 自己在 `package.json` 里声明过的依赖**。幽灵依赖从根上不可能发生。这一点在 monorepo 里尤其重要，因为包多了，幽灵依赖的概率成倍增长。第 3 章会画出这个结构。

### 优势二：磁盘与速度

pnpm 把所有版本的包存在一个全局的**内容寻址存储（content-addressable store）**里，项目的 `node_modules` 通过硬链接指向它。同一个 `zod@3.23.4` 在你 50 个项目里只占一份磁盘。monorepo 里多个包共享同一版本时也是硬链接，安装速度和体积都远优于 npm/yarn。

> 这不是说 npm/yarn 不能用。如果你团队已经在用 yarn workspaces 且没遇到幽灵依赖问题，不必强行迁移。但**新项目 + 多包 + 需要严格边界**时，pnpm 是更稳的默认选择。

## 1.5 什么时候**不该**用 monorepo

工程决策要讲边界。monorepo 不是银弹，以下情况请谨慎：

- **项目之间毫无关联**：把一个后台管理系统和一个游戏客户端放一起，只是徒增仓库体积和 CI 复杂度。
- **团队/权限需要强隔离**：不同仓库可以用 CODEOWNERS、分支保护、访问权限做硬隔离；monorepo 里所有人默认能看到所有代码。
- **发布节奏差异极大**：一个包每天发十次，另一个半年发一次，塞在一起会让版本管理和 changelog 变复杂（虽然 changesets 能缓解）。
- **你还没有「共享」的真实需求**：路线图里写得很直白——「不要为了用 monorepo 而过早拆出十几个 package。最小合理结构是 web、api、db 与 api-client；只有当共享代码有明确边界和使用方时，才抽出 ui/config 等包。」

**判断标准**：当你的多个项目**共享契约、共享类型、需要原子化协同改动**时，monorepo 收益最大。Workboard 正是这种场景：web 和 api 共享 OpenAPI 契约与业务类型，db 被 api 独占但 schema 类型值得复用。

## 1.6 本教程要达成的三个可验证目标

我们不追求「搭一个看起来很专业的 monorepo」，而是追求三个**能被命令验证**的结果。请记住它们，每一章都在为其中之一添砖加瓦：

### 目标 A：可复现（Reproducible）

> 任何人、任何机器，`git clone` 之后，用**固定的几条命令**就能安装、启动、测试，不需要「在我机器上能跑」。

验证方式（第 12 章）：全新目录 clone → `corepack enable` → `pnpm install` → `pnpm build && pnpm test`，全绿。

### 目标 B：可缓存 / 增量（Cacheable & Incremental）

> 改一个包的一行，不必无条件重建全仓；但**真正受影响的下游包**必须被正确重建。

验证方式（练习 4，第 9 章）：连续跑两次 `turbo run build`，第二次应几乎全部命中缓存（`cache hit`）；改动 `packages/shared` 后，依赖它的 `web`/`api` 的 build 缓存应失效并重建，而与它无关的包仍命中。

### 目标 C：有边界（Bounded）

> 前端拿不到服务端专属代码（数据库、密钥）；包与包之间没有循环依赖；且这两条规则由**脚本自动检查并在 CI 失败**，而不是靠 code review 的自觉。

验证方式（第 6 章）：故意在 `apps/web` 写一行 `import { db } from "@workboard/db"`，运行 `pnpm boundaries:check` 应当报错退出。

## 1.7 常见坑（心智层面）

| 误区                                | 正确认知                                                                        |
| ----------------------------------- | ------------------------------------------------------------------------------- |
| 「monorepo = 把所有代码堆一个仓库」 | monorepo 是**有边界的多个包**共存，边界比堆放更重要                             |
| 「pnpm 和 Turborepo 二选一」        | 它们职责不同、接力协作：pnpm 管依赖，turbo 管任务                               |
| 「用了 Turborepo 就一定要远程缓存」 | 本地缓存已能大幅提速；远程缓存是团队/CI 共享的进阶项，可后置                    |
| 「monorepo 里包越多越好」           | 过早拆包会制造无价值抽象；按真实共享需求拆，最小结构 web/api/db/api-client 起步 |
| 「缓存命中说明代码没问题」          | 缓存只保证「相同输入不重复计算」，**不保证正确性**；正确性靠测试，不靠缓存      |
| 「幽灵依赖在我这能跑就行」          | 换个环境/升级依赖就崩；pnpm 的严格结构正是为了在开发期就暴露它                  |
